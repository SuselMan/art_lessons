# #759: snapshot и Undo длинного жеста

Минимальный repro: chunk1(seq1,G) → Dry(seq2) → snapshot2 → chunk2(seq3,G)
→ Undo4(target=chunk2). Клиент отменяет оба chunks, сервер оставлял snapshot2
с пикселями chunk1, поскольку target.seq=3 находится после snapshot2.
Регрессия воспроизведена: plan.coverage.has(L) было true вместо false.

Выбор snapshots теперь учитывает все chunks того же автора и strokeId,
существовавшие до Undo/Redo. Нижняя граница выбирается по самому раннему
затронутому chunk каждого слоя. Чужой автор с тем же strokeId и будущие
chunks не затрагиваются. Revoke по существующему контракту удаляет только
названную операцию и не расширяется до жеста.

Холодный loader разрешает siblings из БД отдельным запросом только для
жестов, на которые действительно ссылаются новые Undo/Redo. Query ограничен
roomId, автором, strokeId и захваченным watermark; обычный вход без таких
контролов не читает тяжёлую историю. Затем существующий fixed-point loader
поднимает нужные исходные слои. Старые blobs и coverage в БД не изменяются.

Проверка: 32 теста selection/loader, 102 теста выбранных snapshot-модулей
(наборы перекрываются), server typecheck. Негативные случаи: чужой автор,
будущий chunk, cross-layer erase, revoke, redo и более ранний безопасный snapshot.
Реальный HTTP/Socket cold-join повтор проводится после согласованного рестарта
общего QA backend; до него исправление в работающем процессе не применяется.
