# Приоритет пера v10: показать промежуточное растекание

Живая проверка Ильи 11.10 16:36: в v9 даже один штрих после Dry ждёт около5s,
затем резко высыхает. V9 не исправил сушку. Отдельной модели здесь нет.

Причина в коде: material presentation заменяет слой до полной готовности
канонического материала; hidden wash reveal не обновляется. После готовности
reveal пересевается из preview и получает300ms на переход.

V10 (только DEV reviewInputPriority + reviewProgressivePresentation) передаёт показ physical reveal, когда все
принятые команды нанесения этого слоя исполнены, слой не рисуется, а его solver
ещё работает. Начальная картинка reveal берётся из видимого preview; его pending
физическая цель не заменяется. Ресурсы preview сохраняются до canonical finish,
но больше не закрывают рассчитанные промежуточные состояния. Существующий
reveal clock следит за изменениями рассчитанной цели.

Если новый штрих начинается во время этого растекания, preview сначала
пересевается из видимой reveal-картинки; затем native кисть наносит новый ввод.
Канонический материал и порядок исполнения не меняются. Старый v8 без priority
не включает этот переход. Онлайн комнаты не включают этот DEV режим.

Ограничение: до первого рассчитанного промежуточного состояния краска ещё не
движется. Исполнение deposition и solver пока не ускорено. Это исправление
скрытого показа, не гарантия немедленной сушки/плавности на устройстве.
Побайтная эквивалентность production здесь отдельно не доказана.

Проверки: unit FIFO, SettleQueue, washReveal; browser priority-v10-diagnostic.json
проверяет передачу показа ДО завершения solver, повторный DOWN и снимает
состояния очереди после второго UP. Завершение двух штрихов НЕ подтверждено. Художественный результат требует живой оценки.
Новых служб нет, собственный тестовый браузер закрывается в finally.

Отрицательная первая проверка: передачу progressive слоя и повторное
нанесение удалось подтвердить, но canonical ready после второго UP не пришёл
за120s на SwiftShader. Найден дополнительный display loop while pending.
В повторной версии pending solver не запускает собственный непрерывный
display loop: промежуточные публикации запрашивают показ сами; завершённый
reveal сохраняет свой animation loop. Причина timeout этим ещё не доказана.

Повтор без pending display loop также превысил120s readiness после второго UP.
Это не доказанная причина первого timeout. V10 изолирован флагом progress=1,
обычный priority=1 сохранён как v9. Вариант не предлагается как готовое
исправление сушки. Два собственных браузера проверок закрылись в finally.

Диагностика после второго UP: queue26, stroke=null, error=null, context не
потерян. Solver next53→89→115→130, ops220→220→224→230. Прогресс есть;
timeout не доказывает deadlock. Эти показания не являются latency benchmark.
