# Активный материал, base и film: проверяемый контракт

Аудит 09.10.2026, без изменения физики. Источники:
`webgpuCanonical/tileScratch.ts:47`, `sourcePhaseExecutor.ts:55–97`,
`passes/fieldOps.ts:32,157`; подготовленный readonly observer —
`harness/728-room-moment/stage-probe.mjs`.

| Роль | Значение и ограничение |
|---|---|
| inkLoad / inkColor | Текущие нормализованные P/C записи после source landing |
| inkBase / colorBase | Снимок load при смене materialGesture; не доказанная «неподвижная масса» |
| strokeInk / strokeColor | Накопленный source film текущей gesture; MAX не равен сумме доз |
| inkSettled / colorSettled | Отдельные снимки осадка; отсутствие необходимо сохранять явно |

`filmBuffers` один раз при смене materialGesture копирует load в base и очищает
film. Между source сегментами base сохраняется; source landing независимо для
P/C применяет mode1 к base и текущему film. Для k=f=1 идеальная CPU запись:
`fit(v)=round(255*v/max(255,max(v)))`.

Проверяемые инварианты:

- Readonly публикация native результата в GL не меняет ни одну из восьми ролей,
  включая отсутствие ресурса. Это доказывает observer lifecycle, а не физику.
- При неизменном base и кумулятивном MAX film итог не зависит от разбиения одного
  и того же набора контактов на порции. Очищение film и rebase между контактами
  меняют уравнение источника, даже без переноса пигмента.
- Каждая fitted запись конечна и ограничена u8. Между независимыми P/C fit нельзя
  требовать C<=P.B. Условное RGB<=C.A сохраняется MAX/add/fit, если выполнялось
  у всех входов; его нельзя навязывать произвольным реальным optical моментам.
- Консервативный перенос уже записанных каналов сохраняет их Q8 суммы, но это
  не доказывает сохранение исходной физической дозы до fit. MAX и fit неинъективны.
- Нельзя подменять historical settled snapshot техническим continuation base:
  `max(load-snapshot,0)` после такого rebase может обнулить mobile budget.

Минимальный CPU пример: base=[200,0,0,200], два source film
[100,0,0,100] и [0,200,0,200]. Неизменный base плюс MAX film даёт
[191,128,0,255]; последовательное rebase/очистка film даёт [143,112,0,255].
Это различие формулы, а не ошибка округления. Отдельный неинъективный пример:
fit([255,0,0,255])=fit([510,0,0,510]), хотя исходные totals отличаются вдвое.

`wetSourceStateContract.test.ts` содержит эти примеры и 500 условных RGB/A
fixtures. Это идеальная CPU-Q8 алгебра, не обещание точного аппаратного округления.
Предыдущий `wetBrushMomentCarrierCounterexample.test.ts` отдельно фиксирует
потерю mobile после refresh исторического snapshot и signed/clamped различие.

Подготовленный A wetmix gate наблюдает три контакта (вода, фиолетовый, жёлтый),

## Привязка к реальному callsite и минимальный диагностический вариант

`CanonicalRoomWatercolorExecutor.emitPrepared` сначала выполняет
`source.execute`, который снова пишет `inkLoad/inkColor=mode1(base,film)`.
После этого `publishCurrentToGl` для moment-кандидата вызывает transport. При
ненулевой GPU-audit рецептуре затем копирует изменённый load в base и очищает
stroke film. Это точный мост к CPU counterexample выше: техническое сохранение
переноса между контактами одновременно меняет нормализацию источника и выбор
mobile snapshot. В copy-ветке такой rebase делает `WetBrushMomentSourceSeam`.
Zero-state ветка уже отдельно доказала отсутствие этого rebase.

Просто убрать копирование/очистку нельзя назвать исправлением: следующий
`source.execute` перезапишет перенесённый load из старых base+кумулятивного film.
Минимальный безопасный вариант **R (только диагностическая ветка)**:

1. Canonical load/base/film/settled и gesture эпохи остаются неизменными.
2. После source landing создать вспомогательную копию P.B+четырёх C-каналов,
   применить оператор только к ней. P.R/G/A не переносить.
3. Показать эту копию в отдельном диагностическом сравнении с canonical output;
   не отдавать её production settle/planner и не называть постоянным переносом.

Это разрешает исследовать контакт/направление без source rebase и сохраняет
reference целиком. Но такой результат не накапливает прошлый перенос между
контактами, поэтому не удовлетворяет сам по себе задаче живого перемешивания.
`wetSourceReadonlyBranch.test.ts` явно проверяет этот предел и неподвижность
восьми canonical ролей (включая null snapshot).

Для постоянного active-варианта пока не хватает данных/контракта:

- Реальные cropped pre/post source load, base, film, settled и gesture epochs
  второго цветного контакта; подготовленный readonly observer их соберёт.
- Scale до независимого P/C fit или иной достаточный ненормализованный carrier:
  source записи не позволяют восстановить prefit dose.
- Исторический settled snapshot отдельно от continuation base, captured до
  первого переноса, с определённым signed/clamped mobile budget.
- Контракт приращения новой дозы в перемещённый carrier: разность двух fitted
  source состояний может быть отрицательной. CPU пример даёт red delta−64;
  после полного вывода red из прежней клетки слепая инъекция создаёт−64,
  а clamp добавляет64. Никакой физической «починки» clamp этим не обоснован.

До этих наблюдений/решения вариант R остаётся отдельным readonly экспериментом,
не интеграционным патчем и не обещанием художественного улучшения.

### Общий участок и независимый растворитель (офлайн, 09.10)

Следующий контроллер фиксирует мировую область `[402,352,78,96]` внутри фактических прямоугольников всех трёх контактов. Выход за прямоугольник — ошибка, область не сдвигается. Пакет содержит 17 прежних материальных/экранных стадий и четыре явно названные дополнительные стадии настоящих `solventLoad`/`foreignSolventLoad` до и после публикации. P.R и coverage не подменяют V. Отсутствующая текстура отмечается `absent`, а не синтетическими нулями.

Строка GPU выровнена до 512 байт; передача удаляет padding и сохраняет 312 байт на строку. Строгий decoder проверяет схему 21 стадия, одинаковые мировые координаты, временную отметку наблюдения и бюджет 3 MiB, освобождая каждый base64 payload после SHA/долговечной записи. Худший бинарный объём при всех присутствующих полях — 1 886 976 байт (`3*21*78*96*4`). Это диагностический наблюдатель с прежним общим 120-секундным дедлайном, не измерение задержки пера.

В прежней аппаратной серии `inkSettled/colorSettled` отсутствовали во всех трёх контактах. Это доказывает отсутствие данных в этих конкретных слотах, а не отсутствие пигмента или воды. Источник текущего film остаётся `inkLoad/colorLoad` через снимок base и MAX-накопление film; новый materialGesture меняет epoch. Поэтому нельзя вычислять «мобильную массу» вычитанием отсутствующего settled или трактовать base как гарантированно неподвижный осадок. Предстоящие снимки V и история импортированных жестов нужны отдельно: фактическое количество/состояние жидкости из этой одной проверки отсутствия не следует. Публикация без транспортного оператора обязана сохранять все восемь материальных ролей, их отсутствие и обе реальные V-роли.

Новая аппаратная серия ещё не запускалась. Офлайн проверки покрывают полную схему 21 стадии, SHA/ACK, явное отсутствие, выравнивание строки, отказ при несовпадении мировых координат и сохранение первичной ошибки.

### Следующий офлайн proof: граница settle, без новой физики

Исходники показывают конкретный путь между предыдущим source и новым base. `RoomNativeRuntime.finish` ставит `owner.prepareSettle` в центральную FIFO после готовых source-пакетов. Planner выбирает прежнюю неподвижную часть как текущий `inkBase` при совпавшем filmGesture, иначе settled-слот, иначе load. Отсутствие settled при поддержке film намеренно допустимо: отдельные settled-текстуры выделяются только в ветке без film. В `CanonicalWatercolorSettlePlan.land` итог поля возвращается в load либо в base более нового running film; затем цвет и coverage также обновляются. Следующий `filmBuffers` копирует текущий load/color в base нового materialGesture. Значит изменение предыдущего source→следующего base совместимо с настоящим промежуточным settle; это локализуемая гипотеза из кода, ещё не доказательство конкретных 27375 Q8 единиц.

Подготовлен отдельный readonly наблюдатель `settle-boundary-probe.mjs`: первый GPU copy общего мирового ROI **до** вызова planner.prepare; второй — **после** завершения canonical job.finish и composite encode. Чтение staging выполняется в существующем task.publish, исходный publish вызывается один раз, оригинальные finish/step/dispose/физические параметры не заменяются. Снимки включают те же восемь ролей и две реальные V-роли с явным отсутствием, actual gesture/material/film/solvent epochs, foreign gesture IDs, bounds и диагностическое время. Нулевая job отмечается skipped без выдуманных полей.

Opt-in контроллера: `QA_SETTLE_BOUNDARY=1`, только существующая tip-wetmix серия A/momentOFF/frozen5362. Максимум три job, два снимка по десять полей, не более2MiB бинарных данных; теоретический максимум1 797 120 байт. Предыдущий source-пакет ≤3MiB остаётся отдельным и общий readback≤32MiB. ASCII/base64 снимается последовательными bounded chunks с SHA/fsync/ACK, буферы освобождаются после чтения, dispose или восстановления хуков. Дедлайн120 и guard1700/500 сохраняются. Офлайн единая интеграция snapshot→padded512/tight312→decoder→ACK проверена, включая отсутствие settled и неуспешный настоящий publish. Новая аппаратная серия не выполнялась.

Цель сравнения: previous source/post → before-prepare → after-finish → next base на **одинаковых мировых пикселях**. Только после такого совпадения можно приписать локальную разницу конкретной фазе. Даже тогда ROI не представляет полный баланс массы wash.

### Приоритетный контракт raw V против coverage (офлайн)

Native raw `solventLoad` не имеет другой раскладки относительно production WebGL. В обоих случаях source-штамп получает opacity=`waterDose/4`, inkWater1, paperWet0, inkStrength0. Ribbon solvent vertices также имеют water1/paperWet0/strength0. Общая формула целевого P — `(amount*water,amount*wet,amount*strength,amount)` — поэтому raw V записан `(amount,0,0,amount)`. Источники: `RibbonStrokePainter.ts` solvent phase, `canonicalStrokeChunk.ts` solvent commands, `canonicalRibbonBands.ts` solvent vertices; GL `shaders.ts` DAB/RIBBON deposit и native `stamp.ts`/`deposit.ts`. Source-contract тест проверяет эти фактические рецепты и формулы, не GPU parity целой комнаты.

| Связанный ресурс | R | G | B | A |
|---|---|---|---|---|
| raw solventLoad | водяная доза/4 |0|0| водяная доза/4 |
| pigment inkLoad | amount×brush water |amount×paper wet|amount×pigment strength|amount |
| coverage | across×coverage |poolness×coverage|available standing water×coverage|coverage |

Следовательно `V.b/V.a` в consumer корректен только если texture binding действительно означает coverage/соответствующий prepared water-domain. Для raw solventLoad этот коэффициент равен0 при ненулевой воде. `V.r/V.a` raw V равен1 и **тоже не измеряет толщину**: сама доза хранится вA (с reservoir масштабом4), а относительная wetness/appearance относятся к другим ресурсам. Перед исправлением presentation-domain нужно проверить identity фактически связанной текстуры; нельзя переименовать канал или заменить input на основании имени переменной `V`. Runtime/шейдеры/defaults в этом аудите не менялись.

### Узкий operator trace и кандидат оптимизации (офлайн)

`settle-write-trace.mjs` готов как opt-in `QA_SETTLE_TRACE=1` прежнего контроллера. Только metadata: максимум3job/32записи в реальные tile-слоты, ring последних8 GPU API calls, счётчики по методам; новых GPU readback/copy/fence нет. Каждая запись содержит actual field identities/role, mode/rect и текущую phase (`prepare`, `step-N`, `finish`). Delegates вызываются ровно один раз, локальные owner/adapter методы восстанавливаются при dispose/ошибке/cleanup. Тест подтверждает последовательность temporary-resample→copyRegion(load), firstLoadWrite phase=finish и восстановление.

По исходникам первая запись окончательного wet load ожидается в `planner.land → fromField`: при S1 прямой copyRegion(fieldResult→load), при S2 `landResampled` (resample нового результата относительно old/base через pooled temporary, затем copyRegion→load). Это возврат уже вычисленного transported wet-state. Dry/tideline отдельно пишет inkDry/colorDry, а не должно объясняться как потеря load лишь из-за отсутствующего inkSettled. Аппаратное подтверждение точного метода/порядка trace пока не выполнялось.

Конкретный кандидат — уже существующий OFF `diagnosticDirectResample`: исключить temporary/copy в landing **только когда target не совпадает с sampled base/source/old**. Риск: типичный base может быть тем же load, тогда прямое выполнение создаёт запрещённый read/write feedback; этот случай нельзя ускорять тем же способом. Trace покажет фактическую долю eligible и число/размер копий, но CPU submission count не обещает wall/GPU выигрыш. Физические формулы/квантование/порядок solver для оптимизации не меняются. Необходимый gate: actual alias predicate, all-role hashes и whole layer quality plus independent timing. Runtime/defaults здесь не включались.
