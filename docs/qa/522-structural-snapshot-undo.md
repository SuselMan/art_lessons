# #522 — клиентский checkpoint при структурном Undo

Основа `d72567e84c159ed286c56ea6ddcd1450de349fe6`, трек #825.
Эта поставка добавляет регрессию уже существующих клиентских исправлений.
**Issue #522 остаётся OPEN: серверный пункт3 не выполнен.**

## Что проверено

В текущем main `_destroyBuffer` снимает pin у snapshot checkpoint, сохраняя
его доступным до обычного вытеснения. Если checkpoint уже вытеснен, пересборка
слоя с сетевым coverage запрещает его публикацию. Реализация уже была в коде;
новая проверка не меняет runtime и не приписывает себе её исправление.

`e2e/specs/structuralSnapshotUndo.spec.ts` создаёт настоящий WebGL-рисунок,
бэйкает сетевой снимок100 и передаёт его второму движку. У второго **нет ни
одного исторического stroke**: восстановить рисунок переигрыванием старых
штрихов он не может. Проверка содержательного пиксельного массива даёт2639
непрозрачных пикселей исходного рисунка, а не пустой эталон.

Для delete и merge (два исходных слоя) выполняются две ветки:

| Ветка | После уничтожения слоя | Undo | Bake |
|---|---|---|---|
| Достаточный бюджет | checkpoint сохранён, уже не pin | исходные пиксели | разрешён, RGBA diff0 |
| Бюджет0 | pin защищает живой слой; после уничтожения происходит настоящее вытеснение | локально может не хватать базы | `null`, неполные пиксели не публикуются |

Затем устанавливается исходный сетевой снимок заново: обе ветки снова
разрешают bake, RGBA diff0. Это проверяет, что отказ не превращается в
постоянную невозможность сохранять исправленный слой.

Матрица4 случая на Chromium/SwiftShader и4 на настоящем Samsung SM-T970,
Adreno650. Все восемь случаев прошли. Первый отдельный Chromium-прогон:
1 PASS/1 SKIP,32,8с. Общий Chromium+Samsung:2 PASS,64с со стартом стека.
Бумага загружена до рисования; сравниваются байты encode/decodeLayerTiles.
Это API движка и реальные шейдеры, не Socket.io/физический S Pen или OOM.
Бюджет меняет настоящий CheckpointStore, а не подменяет функцию lookup.

Отложенные fetch превью других вариантов бумаги были отменены при закрытии
собственной QA вкладки; соответствующие console errors появились после
пиксельных assertions. Каждый движок дождался своей paperReady.

## Что остаётся

Сервер в snapshotStore хэширует распакованные данные и сравнивает повторные
поставки **одного seq**. Проверки резкого падения размера между seq нет.
Поэтому пункт3 не объявляется готовым и checkbox #522 в #825 не отмечается.

Размер gzip сам по себе не является инвариантом сохранности: законная очистка,
плоская заливка и удаление заэкранных пикселей тоже резко уменьшают файл.
Один автоматический порог с отказом или `disputed` без правил восстановления
может удерживать старое coverage и растить replay-хвост у корректного рисунка.
Логирование одной аномалии, напротив, не запрещает ошибочному кандидату стать
coverage. Эти два поведения нельзя выдавать за один выполненный критерий.

Нужен согласованный контракт проверки кандидата: где он хранится до проверки,
какой снимок остаётся читаемым и как подтверждается законное уменьшение, в том
числе когда в комнате один клиент. Клиентские проверки выше готовы независимо
от выбора этого серверного механизма.
