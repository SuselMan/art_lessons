# #774: почему ввод продолжает отображаться при suspendDisplay

Read-only review кандидата6b196577. Аппаратная проверка другого агента выполнена
на `d70e9260d9abfd787dd187cf5357cbfa78289127` и сохранена вкоммитах25c340ed/e87c9388,
`docs/qa/runs/728-undo-v1-2026-10-16/774-held-public-screen-proof.json`.

Предположение о заморозке MOVE не воспроизвелось. В publicRoomrestore реально
были deferred=true, signal=true иdisplayDepth1 непосредственно после defer.
ДоUP, покаrestoredone=false, дальнейшее движение изменило432RGB-канала farROI
(max115), ранний штрих сохранился безизменений. ПослеUP actual и независимый
oracle совпали; GL/page errors0. Depth повторно послеMOVE не измерялся — не
приписываем аппаратному прогону дополнительное наблюдение.

Исходники объясняют результат безнового runtime изменения:

* `index.ts` `_onMove`: после реального рисования `painted` прямо вызывает
  `_scheduleDisplay()` (около7018).
* `_scheduleDisplay` (около10230) ставитRAF и прямо вызывает `_display()`.
* `_display` (около10261) отказывается только приcontext loss. Guardпо
  `_displaySuspendDepth` здесь отсутствует; этот путь обслуживает живой ввод.
* Проверкаdepth находится в `_displayIfNotSuspended` (около2883–2893), который
  используется append/rebuild/batch обновлениями. PointerMOVE его обходит.
* `_onEnd` также вызывает `_display()` прямо (около7150).

Таким образом, batching сетевого восстановления и обновления живого ввода имеют
разные существующие входы. Deferredbitmap сохраняет живые pixels/FBO, а обычный
input продолжает показывать их через свой RAF-путь. Ни снятияbatchguard, ни
форсированногоdisplay в тестовомоператоре для получения результата не было.
Это конкретная проверка карандаша, не новая универсальная гарантия всех инструментов.
