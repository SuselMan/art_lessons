# #802: почему UI RAF достигает200мс на Samsung

**Исправление22:36:** вывод об исключении очереди GPU отозван. В точной версии Chrome `gl.finish()` вызывает толькоFlush. Девять вызовов0–0.1мс не являются GPU-синхронизацией. Swap throttled2/2 остаётся наблюдаемым промежуточным состоянием; незавершённая GPUработа всё ещё может быть его причиной. Ниже сохранён ход проверки; контроль с настоящим readback выполняется отдельно.

Продолжение с настоящим чтением материала установило значительное ожидание уже в нативном расчёте растекания, до окончательного смешивания. См. [актуальный отчёт](../802-gpu-queue-20261017/findings.md). Это не200мс работы UI JavaScript; сам по себе вынос в Worker не освобождает общий GPU. Ниже сохранены промежуточные контрольные прогоны и трасса, а не окончательное объяснение причины.

## Что увидели

На Samsung SM-T970/Adreno650 проверены3последовательных одинаковых мазка320/PB15 на локальном Worker Mini1024. Следующий мазок начинался после готовности предыдущей цели и окна морфинга; во время измерения не делались скриншоты/PNG. Стенд пользователя и его рисунок не менялись. Инструментирование и контрольные замены применялись только к HTTPответам собственных браузерных контекстов.

В исходном варианте максимальная пауза между RAF-кадрами216.1мс. Во время этого промежутка обычный таймер выполнился20раз, интервалы до10.6мс; сообщения main заняли суммарно1.7мс. LongTask main отсутствовали. За весь прогон самый длинный обработчик сообщения6.4мс, RAF-callback6.9мс, запись диагностики вDOM1.2мс, getBoundingClientRect0.4мс. Это измерения выбранного прогона, не универсальные гарантии.

В исходном прогоне во время движения пера RAF-интервалы не превышали28мс. Самые большие паузы были после JS-сигнала готовности цели:86/148/216мс по трём мазкам.

## Контрольные прогоны

| Изменение только в диагностическом контексте | Результат |
|---|---|
| Исключена запись полного JSON диагностики, всё остальное сохранено | Максимум паузы кадров150.5мс, обработчик сообщений до2мс. Лишняя CPUработа уменьшена, сама проблема остаётся |
| Исключён только периодический engine._display(), morph shader сохранён | После целей147/184/205мс паузы кадров: полный вывод/бумага/blit не являются единственным объяснением |
| Исключены периодические morph tick и display, расчёт/начальный setTarget/статусы сохранены | Паузы148/117/153мс остаются: сами повторные кадры морфинга не являются достаточным объяснением |
| По одному gl.finish после цели,6draw подготовки морфинга и окончания первого RAF с целью | Ровно9барьеров на3цели, каждый0–0.1мс ожидания; пауза RAF всё равно236.9мс |

gl.finish в этой версии Chrome толькоFlush. Этот контроль НЕ проверяет завершениеGPU; отсутствие ожидания не позволяет исключать очередьGPU.

Сам стенд действительно делает лишнее:681пересборка/запись диагностическогоJSON,45.6млн символов,577.6мс stringify суммарно за весь исходный прогон; максимум одной сериализации5.9мс. Поэтому это имеет смысл убрать из закрытой панели, но приписывать ему один скачок200мс нельзя. Рабочая страница в этом расследовании не менялась.

## Короткая трасса Chrome

После двух прогревочных мазков снята одна ограниченная трасса третьего мазка: от момента перед UP до готовности цели+1с. С учётом накладных расходов трассы поймана149.1мс пауза RAF. Относительно начала паузы:

- Android Extend_VSync продолжает приходить примерно каждые16.7мс.
- На+11.64 и+15.24мс Chrome Viz отмечает `Swap throttled`: `pending_swaps=2`, `max_pending_swaps=2`.
- Пока очередь заполнена, новые BeginFrame не доставляются main и worker, хотя обычные таймеры идут.
- На+145.24мс приходит `GLSurfaceEGLSurfaceControl::OnTransactionAckOnGpuThread`; ожидание снимается, BeginFrame возобновляется примерно+145.6мс, main RAF — около+149мс.

Это прямое наблюдение обратного давления очереди показа: Chrome ждёт подтверждения двух уже отправленных кадров. Почему подтверждение задержалось, эта браузерная трасса не доказывает. Нельзя объявлять это багом Android или гарантировать устранение одним изменением JS/шейдеров. Схожая поздняя выдача RAF ранее наблюдалась и на исходном Mini без Worker, поэтому OffscreenCanvas не объявляется единственной причиной.

Отдельно, раньше этой паузы при расчёте цели трасса показывает86.4мс в worker GLES2::ReadPixels/ожидании команды. Это другой участок времени; его нельзя складывать с последующей паузой RAF как одну задачу main.

Доказательства: `docs/qa/harness/802-ui-profile/samsung-summary.json` и `samsung-trace-summary.json`. Сохранены SHA источников/входа и компактная выборка событий; приватная сырая трасса удаляется после проверки компактного итога. Проверка выполнена только на Samsung; системная трасса Android/SurfaceFlinger и другие устройства не проверены.

Уборка завершена:6собственных измеренных контекстов и служебная вкладка закрыты, forward19336 снят, reverse не создавался. Новых серверов нет, опубликованный стенд не менялся. Временный каталог и сырая10МБ трасса удалены после сохранения компактных доказательств;5сжатых отчётов меньше1МБ сохранены приватно внеTTL вместе с manifest. Код измерителя и компактные доказательства — коммитe83ff313.
