# #850 — как ускорить переходы между досками

По замыслу смена доски должна использовать один сокет урока. Но сквозная проверка
с четырьмя переходами показала пересоздания соединения. В коде есть конкретная цепочка:
`boardId` → `repairSnapshotHistory` → `backfillHistory` → `restoreRoom` → эффект сокета.
При переходе меняется callback, и эффект переподключает сокет. Эта зависимость есть уже
в исходном `b85a31822`, а не добавлена исправлениями этого списка.

Кроме этого, переход ждёт отправки незавершённых действий, запрашивает `room_state`,
завершает старый движок и собирает новый из снапшота и хвоста истории.
Время каждого этапа отдельно пока не измерено.

Что можно сделать, по возрастанию сложности:

1. Сначала стабилизировать зависимости эффекта сокета, сохраняя правильную привязку
   восстановления к доске; проверить отсутствие повторных входов и гонок.
2. Сразу показывать сохранённое превью новой доски, пока идёт восстановление. Это улучшит
   ощущение перехода, но само время готовности рисовать не сократит.
3. Заранее загружать каталог и ресурсы кистей соседних досок, переиспользовать проверенные
   неизменяемые данные. Потенциально уберёт сетевые ожидания; нужны ограничения памяти
   и сохранение проверок прав доступа.
4. Держать ограниченный кеш состояния недавно открытых досок и догружать только новые
   операции. Это может заметно ускорить возврат, но требует строгой проверки актуальности,
   памяти GPU, undo и незавершённых действий. Держать все движки постоянно не стоит.

Предлагаю сначала убрать лишние переподключения и измерить этапы, затем сделать
превью + предзагрузку. О кеше решать после измерений.
Это предложения для отдельного обсуждения; оптимизации не реализованы.

`pages/Room/index.tsx` (переход/создание движка), `pages/Room/useRoomRestore.ts`.
Пути относительно `apps/web/src`. Основа анализа: `b85a31822`.
