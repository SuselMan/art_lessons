# ADR 012: Единый API геометрии отпечатка

## Статус

Proposed (2026-08-22). Определяет скоуп #482.

**Вне релиз-трека.** Не мапится ни на один пункт #314: в §3 «Качество инструмента»
открыт единственный пункт #475 (калибровка нажима пера), и он про вход, а не про
форму следа. Это дорелизная архитектурная работа, которая разблокирует качество
акварели (ADR 011) и любой следующий инструмент. Заводить ли пункт в трек —
решение Ильи.

Ничего не меняет в Operation Log: `Dab` остаётся тем же (`packages/shared`), поля
те же, старые операции реплеятся как реплеились. Это условие, а не побочный
эффект — см. §4.

## Контекст

### Отпечаток собирается в четырёх местах

Форма пятна контакта считается сегодня четырьмя независимыми кусками кода, и три
из них — копии первого, разошедшиеся в разной степени.

1. **`DabSystem._makeDab`** (`engine/src/DabSystem.ts:728`) — основной путь, через
   `DabShapingProfile` (`engine/src/dabShaping.ts`). Единственный, который знает
   про фильтры входа и про состояние наконечника.

2. **`PencilEngine._paintDwellDab`** (`engine/index.ts:5661`) — вторая реализация,
   написанная руками. Не идёт через `DabSystem` вообще: сама дёргает
   `shaping.size/aspect/angle`, сама собирает `Dab`, хардкодит `angle: 0` для
   всего кроме маркера, не знает ни про фильтр давления, ни про `tipBend`. Сходит
   с рук ровно потому, что `dwellConfigForTool` отдаёт конфиг только линеру и
   маркеру, а у них состояния нет.

3. **`previewDabShape`** (`engine/index.ts:120`) — третья, и она честно объявлена
   зеркалом: «mirrors `DabSystem._makeDab`'s own geometry formula exactly».
   Зеркало, которое поддерживают руками, уже разошлось: оно не знает про `tipBend`,
   поэтому курсор кисти для пера рисует круг, пока инструмент кладёт изогнутый
   эллипс.

4. **`applyBrushPenHeadTaper` / `applyBrushPenEndTaper` / `applyBrushPenSpeedContact`**
   (`engine/src/brushPenPresets.ts`) — три пост-процесса, которые правят `dab.size`
   **после** того, как форма уже посчитана. Побочный эффект прямой: `elongation`
   и дальность изгиба `lagPx` считаются по нетейперенной ширине, то есть на первых
   10 px штриха наконечник «шире», чем нарисован.

Четыре места не потому, что кто-то плодил копии, а потому что `DabShapingProfile`
не умеет выразить часть входов, от которых форма реально зависит. Всё, что не
влезло, уехало наружу.

### Что из этого выросло

**Смешанные системы координат.** `tiltOrPathAngle` — угол по умолчанию для
карандаша, ластика, растушёвки, линера и угля:

```
tiltMag > 15 ? atan2(tiltY, tiltX) : pathAngle
```

`tiltX/tiltY` приезжают из браузера в **экранных** координатах и доходят до
движка нетронутыми (`engine/index.ts:5169`), `pathAngle` — **мировой**. Оба
уходят в мировой `Dab.angle`. Компенсации `_infiniteCamera.angle` в тракте формы
нет нигде. На повёрнутом холсте (вращение есть с #319) наклонённое перо кладёт
эллипс не туда, и инструмент переключается между двумя привязками посреди штриха
на пороге 15°.

**Ширина не вся в `Dab.size`.** Итоговая полуширина — это
`dab.size * 0.5 * preset.sizeMultiplier`, и множитель применяется на отрисовке
(`_dabWorldHalfExtents`, `_paintDabsInstanced`, `markerRibbon.nibGeometry`), а не
запекается в даб. У графита он ходит 0.5…1.6 по грейдам, у угля 1.10…1.20. Ластик
его обходит целиком (`erasing ? 1.0 : preset.sizeMultiplier`) — не решением, а
булевым флагом, протянутым через весь пайплайн.

**Сглаживание входа зависит от железа.** #472 перевёл сглаживание нажима с веса
на сэмпл на расстояние (`pressureSmoothingPx`), потому что per-sample фильтр имеет
частоту среза, равную частоте опроса планшета: одна и та же рука на 240 Гц
получала втрое меньше сглаживания, чем на 60 Гц. Но:

- акварель осталась на легаси-ручке `pressureSmoothing: 0.55`, причём её
  комментарий и тест читают направление наоборот (фильтр `y += (u−y)·k`: больше
  k — **слабее** сглаживание);
- **сглаживание наклона так и осталось per-sample** (`_filterTilt`, ручка
  `tiltSmoothing`) — тот же дефект, просто до него не дошли руки.

## §1. Отпечаток — это поза, а не форма

Тройки `{size, aspect, angle}` недостаточно: перо ещё и **смещает** даб назад по
направлению наконечника (trail, `_makeDab` вычитает `_trailPx` из `x/y`). Это
единственный инструмент, который снимает даб со сплайна, и это часть отпечатка,
а не отдельный эффект — контактное пятно изогнутого наконечника физически лежит
позади оси.

```ts
interface TipFootprint {
  /** Короткая полуось, world px. На прямой полуширина следа — это она и
   *  только она, поэтому именно она, а не «размер». */
  halfWidth: number
  /** Длинная / короткая. 1 = круг. */
  elongation: number
  /** Мировые радианы. Как получен — см. §3. */
  angle: number
  /** Смещение от точки на сплайне, world px. {0,0} у всех, кроме гибких. */
  offsetX: number
  offsetY: number
}
```

Почему `halfWidth`, а не `size`: длинная ось у гибкого наконечника лежит **вдоль
хода**, поэтому на прямой линии она в ширину следа не входит вообще. Называть
«размером» величину, которая на прямой видна только с торцов и на поворотах —
ровно та путаница, из-за которой в v1 пера ширина и вытянутость воспринимались
как две ручки одного эффекта.

`preset.sizeMultiplier` остаётся снаружи и применяется на отрисовке, как сейчас
(см. §7 про то, почему не запекаем).

## §2. Входы

Полный список того, от чего отпечаток зависит. Помечено, что уже есть.

| вход | сегодня | система координат |
|---|---|---|
| `pressure` | есть, сглажен | — |
| `tiltX/tiltY` | есть, сглажен у графита и угля | **экранная**, объявить явно |
| `pathAngle` | есть | мировая |
| `ds` — дуга от прошлого дабa | есть | world px |
| `arcFromStart` | только у пера, снаружи | world px |
| `arcToEnd` | только у пера, снаружи, только на отрыве | world px |
| `speed` | есть | canvas px/ms |
| `dwellMs` — время под контактом | есть, но только в потоке | ms |
| `inkLoad` — сколько уже выложено за штрих | попиксельно в шейдере, на форму не влияет | — |
| `twist` — прокрутка пера вокруг оси | **нет вообще** | экранная |
| `baseSize` | есть | world px |

`twist` в `PointerData` (`engine/src/PointerInput.ts:25`) отсутствует: там только
`x, y, pressure, tiltX, tiltY, speed, pointerType, timeStamp`. Поле `e.twist` есть
в спеке PointerEvent, но железо его почти не отдаёт (S Pen не отдаёт). Слот в API
оставляем, реализацию — нет; иначе первый же инструмент, которому он понадобится,
опять уедет наружу.

Вырожденные случаи объявляются контрактом, а не подразумеваются: `pointerType:
'mouse'` — нет нажима (подставляется 0.5), `'touch'` — нет наклона.

## §3. Якорь угла

Угол сегодня получается четырьмя разными способами, и ни один из них не назван.
Называем. Пусть θ — угол камеры (`_infiniteCamera.angle`), φ — направление штриха
на экране.

| якорь | `nib_world =` | смысл |
|---|---|---|
| `canvas` | `offset` | приколот к бумаге. Повернул холст — скос уехал относительно руки |
| `screen` | `offset − θ` | приколот к экрану. Допущение «человек сидит перед экраном ровно» |
| `stroke` | `pathAngle + offset` | приколот к ходу. Толщина перестаёт зависеть от направления |
| `barrel` | `azimuth − θ + offset` | приколот к корпусу пера. Физически единственный правдивый |

Четыре, а не пять: **`stroke` инвариантен к повороту холста сам собой**.
`pathAngle_world = φ − θ`, значит на экране получается `φ + offset`, θ сократилась.
Комбинации «stroke + экранная компенсация» не существует, и добавить её — значит
прибавить θ обратно, то есть испортить.

**`stroke` не даёт каллиграфию, а выключает её.** Настоящий скошенный маркер ценен
тем, что держит угол, *пока направление меняется* — от этого линия и гуляет по
толщине. Якорь к ходу держит наконечник под постоянным углом к движению, то есть
толщина перестаёт зависеть от направления вообще. Это законный режим, но
называть его «следовать за рукой» нельзя.

**`barrel` вырождается у вертикали.** Азимут — это `atan2` двух почти нулей, и
шумит он тем сильнее, чем прямее держат перо. Отсюда существующий порог 15° и
векторный (а не «магнитуда + азимут») фильтр наклона в `_filterTilt`. Поэтому
`barrel` всегда объявляется вместе с запасным якорем.

### Решения

- **Графит, ластик, растушёвка, линер, уголь**: якорь `barrel`, запасной `stroke`,
  порог 15°. Это ровно сегодняшнее поведение, но названное — и починенное:
  сегодня азимут меряется на экране и применяется в мире, то есть промахивается
  ровно на θ. **При θ = 0 новая формула совпадает со старой попиксельно**, то есть
  изменение видно только там, где сегодня неправильно.
- **Скошенный маркер**: дефолт `canvas` (как сейчас), `stroke` остаётся тем, чем
  был `followStrokeDirection` (#278), добавляются `screen` и `barrel`.
- **`tilt` на входе несёт объявленную систему координат.** Иначе каждый следующий
  инструмент будет решать этот вопрос заново и по-своему.

## §4. Состояние наконечника и чистота

Результат запекается в `Dab.size/aspectRatio/angle/x/y` и реплеится у пиров **без
пересчёта**. Отсюда жёсткое требование:

> Модель обязана быть чистой функцией от (входы + явно объявленное состояние
> штриха), а состояние — восстановимым проигрыванием дабов этого штриха по порядку.

Сегодня это соблюдается случайно: состояние есть ровно у одного инструмента
(`tipBend`, ADR 009 §13). Единый API делает его объявленным:

```ts
interface TipModel {
  smoothing?: { pressurePx?: number; tiltPx?: number }
  createState?(): TipState          // нет — значит чистая функция сэмпла
  footprint(input: TipInput, state: TipState | null): TipFootprint
}
```

Жёсткий графит, ластик, линер и уголь `createState` не объявляют и игнорируют всё,
кроме нажима и наклона — для них это ровно сегодняшний `DabShapingProfile`,
переименованный.

Что состоянию **нельзя**: читать холст, читать чужие штрихи, зависеть от wall-clock.
Всё, что нужно от времени, приходит входом `dwellMs`, который считается от
`Dab.t` — то есть запечён и реплеится.

## §5. Dwell входит в геометрию

`DabSystem` выдаёт дабы по пройденной дуге, а не по времени. Пойнтер стоит —
расстояния нет — дабов нет ни для какого инструмента. Для графита это верно, для
чернил нет, поэтому и появился таймерный `_paintDwellDab` (#245).

Сегодня dwell двигает только поток (`dwellFlow`), и в `linerPresets.ts:240` стоит
обоснование, почему он намеренно не расширяет отпечаток. Для стального капилляра
это верно. Для мокрой кисти — нет: стоящая кисть отдаёт воду в бумагу, и пятно
физически растёт.

**Решение: `dwellMs` становится входом геометрии. Поток остаётся.** Оси
ортогональные, opt-in по инструменту: линер получает только поток (как сейчас),
акварель — оба, графит — ничего.

Два следствия:

- `_paintDwellDab` перестаёт быть второй реализацией отпечатка и становится
  вызовом того же API с `ds = 0` и накопленным `dwellMs`. При `ds = 0` вес
  однополюсника изгиба равен нулю, то есть стоящий наконечник остаётся ровно
  настолько изогнутым, насколько был — правильное поведение, которое сегодня
  получается само, но которое никто не проектировал.
- Калибровочная оговорка: если наконечник на месте **и** расплывается, **и**
  темнеет с прежней скоростью — отдача краски посчитана дважды, та же краска
  размазана по большей площади. У расплывающегося наконечника `maxFlow` должен
  быть ниже, чем у нерасплывающегося. Это числа, не архитектура, но при задании
  чисел про это надо помнить.

## §6. Сглаживание входа — по расстоянию, обе оси

Одна ручка на сигнал, обе в **world px пройденного пути**, не в весах на сэмпл:

- `smoothing.pressurePx` — сегодняшний `pressureSmoothingPx` (перо: 10 px).
- `smoothing.tiltPx` — **новое**. Сегодня `tiltSmoothing` per-sample и страдает
  ровно тем же дефектом, который #472 вылечил у нажима: частота среза равна
  частоте опроса планшета.

Легаси-ручка `pressureSmoothing` (per-sample) удаляется. Акварель переезжает на
`pressurePx`; заодно чинится перевёрнутое направление в её комментарии и тесте
(`> 0.35` утверждает «сглаживает сильнее», хотя больший k — слабее).

Пересчёт для миграции — тот же, которым выбирали 10 px: при 500 px/s на 120 Гц
сэмплы ложатся через ~4.2 px, `1 − exp(−4.2/10) = 0.34`. То есть старый вес k
соответствует примерно `−4.2 / ln(1−k)` px.

Сглаживание координат сюда не входит и не войдёт: это работа сплайна, и ADR 009 §3
требует, чтобы нажим сглаживался независимо от координат.

## §7. Что остаётся снаружи

- **Спейсинг и кривизна.** `spacingFactor`, `curvatureTolerancePx`,
  `_curvatureSpacingLimit` — это дискретизация пути, а не форма пятна. Кривизна
  влияет на то, *где* стоят дабы, и не должна попадать в API отпечатка.
- **Осаждение и композит.** `_bakeDabOpacity`, `u_inkMode`, `RibbonProfile` —
  сколько краски и как она смешивается. Этот ADR только про геометрию. Единый API
  осаждения — отдельная работа, и делать их одним заходом не надо: это два разных
  разветвления по инструменту, и слить их в одно — значит получить один большой
  `switch` вместо двух маленьких.
- **`preset.sizeMultiplier`.** Остаётся на отрисовке. Запекать его в отпечаток
  соблазнительно (тогда `Dab.size` наконец означал бы ширину), но старые операции
  его не несут, и после переноса каждый уже нарисованный штрих поехал бы в ширине
  до 1.6×. На проде есть живые комнаты. Поэтому: множитель остаётся снаружи, но
  **объявляется в контракте** — «итоговая полуширина = `footprint.halfWidth ×
  preset.sizeMultiplier`, применяется на отрисовке» — вместо того чтобы быть
  невидимым. Обход у ластика перестаёт быть булевым флагом и становится значением
  `sizeMultiplier: 1` в его собственном пресете.
- **Растеризатор.** Штампы против ленты (`isRibbonTool`) — отдельная ось, её этот
  ADR не трогает.

## §8. Тейперы становятся входами

`applyBrushPenHeadTaper` / `EndTaper` / `SpeedContact` перестают быть
пост-процессами и выражаются через входы `arcFromStart`, `arcToEnd`, `speed`.
Это чинит порядок: сегодня `elongation` и `lagPx` считаются по ширине **до**
тейпера.

Честное ограничение, которое остаётся: `arcToEnd` известен только на отрыве.
Тянуть хвост до подъёма пера нельзя — это латентность на кончике, ровно то, что
вычищали в #104. Поэтому `arcToEnd` объявлен как `number | null`, и модель обязана
давать осмысленный отпечаток при `null`. Это ограничение архитектуры ввода, а не
недоделка API.

## §9. Миграция

Payload не меняется, значит реплей старых операций не ломается ни на одном шаге.

1. `DabShapingProfile` → `TipModel`, `size/aspect/angle` → один `footprint()`.
   Графит, ластик, растушёвка, линер, уголь — механически, поведение бит в бит.
2. `previewDabShape` и `_paintDwellDab` перестают быть копиями и зовут `footprint()`.
   Курсор кисти для пера сразу начинает показывать изогнутый эллипс вместо круга —
   первое видимое подтверждение, что копий больше нет.
3. Якорь объявляется явно. При θ = 0 всё совпадает со старым; на повёрнутом
   холсте становится правильным.
4. Тейперы пера переезжают во входы.
5. Сглаживание наклона переводится на расстояние, акварель — на `pressurePx`.
6. Акварель получает состояние наконечника и dwell (это уже не миграция, а
   работа по ADR 011 поверх нового API).

## §10. Критерии приёмки

- Ни одной второй реализации: `grep` по `shaping.size(` и `shaping.aspect(` вне
  реализации `footprint()` даёт ноль.
- Реплей старых операций попиксельно совпадает с текущим `main` при θ = 0 —
  снапшот-тестом, не на глаз.
- Курсор кисти для пера совпадает с первым дабом реального штриха по
  `elongation` и `angle`.
- Один и тот же жест, записанный на 60 Гц и на 240 Гц, даёт ширины, расходящиеся
  не более чем на порог, — для нажима **и для наклона** (сегодня тест есть только
  для нажима).
- Тот же жест на повёрнутом на 90° холсте даёт тот же след относительно бумаги
  для `canvas` и тот же относительно экрана для `screen`.
- Стоящая кисть с `dwell` в геометрии растёт по ширине и не уходит в разнос
  (ограничена сверху), а изгиб наконечника за время стояния не меняется.

## §11. Открытые вопросы

- Становится ли `barrel` пользовательской настройкой (как отклик наклона в #409)
