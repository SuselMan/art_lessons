# ADR 003: Линер / Fineliner — чернильный инструмент рисования

## Статус

Accepted (2026-07-21). Определяет скоуп эпика «Линер/Fineliner» и его
саб-задач. Первая точка расширения тулсета за пределы графита — см. правку
`docs/MANIFESTO.md` (Vision / Принцип 3) и `docs/TOOLSET.md` от той же даты.
Разделы 3, 6, 8 пересмотрены в тот же день (issue #245) по итогам QA v1 —
см. пометки «Пересмотрено» внутри каждого. Разделы 2 и 3 пересмотрены снова
2026-09-05 (issue #532) — первый раз по расшифровке настоящих дабов из лога
комнаты, а не по рассуждению, и по сверке с физическим линером в руках.

## Контекст

### Что такое линер физически

Одноразовая ручка с пористым/волоконным наконечником и пигментными чернилами.
Характер: линия почти постоянной ширины (нажим/наклон влияют слабо), край
слегка взаимодействует с зерном бумаги, при остановке — небольшое капиллярное
пропитывание, наконечник изнашивается со временем.

Главная метафора: **наконечник, пропитанный чернилами, касается бумаги
небольшой площадью и непрерывно отдаёт жидкость в её волокна** — не карандаш
(материал не накапливается поверх бесконечно, бумага впитывает чернила,
повторный проход почти не темнит уже насыщенную линию).

### Почему это не укладывается в текущий движок как есть

Весь pressure/tilt→геометрия даба код сейчас живёт в одном месте,
общем для всех инструментов: `DabSystem._makeDab`
(`apps/web/src/engine/src/DabSystem.ts`):

```ts
const size       = baseSize * (0.3 + 0.7 * pressure)         // ±70% от pressure
const aspectRatio = 1 + tiltNorm * tiltNorm * tiltNorm * 6.0  // до x7 от наклона
```

Это карандашные диапазоны — нажим и наклон должны сильно менять след. У
линера пресс/наклон должны влиять на 7–15%, не в разы (см. «Решение» ниже).
Сейчас per-tool ветвится только *opacity* (`_bakeDabOpacity`), не форма/размер
даба — значит для линера нужен предварительный рефакторинг: сделать
size/aspect-shaping конфигурируемым per-tool, а не только opacity.

Композитинг (`shaders.ts`, `gl_FragColor = vec4(u_color * deposit, deposit)`
+ alpha-over blend) уже насыщается к непрозрачности сам по себе — не
бесконечно темнеет при повторных проходах. Для линера это в целом подходит,
не требует новой схемы блендинга — только правильную кривую opacity/flow в
пресете (первый проход сразу почти насыщенный).

## Решение

### 1. Форма контакта

Круглый dab, лёгкая эллиптичность от наклона (короткий цилиндрический
наконечник — не длинный эллипс, как у карандаша при наклоне):

```
width  = baseWidth * linerWidth(pressure)          // см. §2 — плато с коленом внизу (#532)
aspect = 1 + 0.15 * tiltNorm                       // не tiltNorm³ * 6, как у карандаша
```

Для Technical Pen/Rapidograph-режима (follow-up, не в v1):
`pressureExpansion = 1`, `aspect = 1` почти всегда.

### 2. Нажим

Слабое влияние на ширину и на flow, никогда не `size = baseSize * pressure`
(это ощущалось бы как кисть/перо, не линер).

**Пересмотрено 2026-09-05 (issue #532), после сверки с настоящим линером.**
Исходная формула `lerp(0.94, 1.08, pressure)` размазывала слабый отклик
равномерно по всему диапазону, и это неверно в обеих половинах сразу. Ilya:
«при очень слабом нажиме он всё-таки рисует тоньше, то есть сильное давление
почти не влияет на толщину, но минимальные значения делают линию тоньше».

Механизм объясняет ровно такую форму: наконечник линера — жёсткий цилиндр.
Как только он полностью сел на бумагу, пятно контакта равно диаметру сопла, и
давить сильнее физически некуда. Ниже давления посадки контакт неполный, и
линия действительно уже. То есть не линейка, а **колено**, причём плоская
половина у него физически точная — поэтому плато ровно 1.0, а не пологий
подъём:

```
width = baseWidth * (pressure >= SEAT ? 1
                                      : lerp(WIDTH_MIN, 1, smoothstep(pressure / SEAT)))
// SEAT = 0.22, WIDTH_MIN = 0.6 — engine/src/dabShaping.ts
flow  = см. §3 и §8: нажим уходит в paper fill (реальный, незажатый Dab.pressure),
        а не в отдельный множитель flow
```

Следствие, названное явно: линия при обычном нажиме стала на ~3-6% тоньше,
потому что старая кривая выше середины диапазона сидела над 1.0. Это
исправление, а не побочный эффект — калиброванные ширины `LINER_SIZES_MM`
задают ширину **посаженного** сопла, и плато — то место, куда калибровка и
должна была попадать.

Маркер за этим не идёт: у него сжимаемый фетровый наконечник, единственное,
чего аргумент про жёсткий цилиндр не описывает (см. ADR 004 §2 и
`markerPresets.ts`).

### 3. Скорость

**Пересмотрено 2026-07-21 (issue #245), после QA v1.** Исходная мягкая кривая
(~1.08 на медленном, ~0.88 на быстром) на практике не читалась глазом.
Согласованная с Ilya модель: чернила вытекают примерно с **постоянной
скоростью по времени**, а не фиксированной порцией на дag — быстрый штрих
размазывает то же количество чернил на большую длину (тоньше/светлее на
единицу длины), медленный — концентрирует (темнее). Это заодно объясняет
dwell (п.6/9) тем же механизмом, доведённым до предела скорости→0.

`flow(speed) = clamp(REFERENCE / speed, MIN, MAX)` — реальная обратная
зависимость, а не линейная: диапазон `[0.5, 1.4]` вместо `[0.88, 1.08]`,
`REFERENCE`-скорость даёт flow=1.0 (baseline).

**Пересмотрено ещё раз 2026-09-05 (issue #532): плато, а не гипербола.**
Физика та же, форма была неправильная — и вскрылось это только после того,
как выяснилось, что `speed` вообще меряли не тем.

Во-первых, баг замера. `PointerInput` считал `dt` по `performance.now()` —
моменту запуска обработчика, а не времени самого сэмпла; события же приходят
пачкой через `getCoalescedEvents()` и обрабатываются в одном цикле. На восьми
настоящих штрихах из лога комнаты (3545 дабов, стилус iPad) это дало: 80.0%
дабов на нижнем клэмпе 0.50, 16.6% на верхнем 1.40, и лишь 3.4% между ними —
при том что реальная скорость руки была 0.24-1.17 px/мс, то есть ровно
обычная штриховка. Отсюда сразу два симптома: «ложится неплотно» (80% чернил
на половинной подаче) и «зебра с равным интервалом» (переключение раз в
кадр). Исправлено в `PointerInput` — время берётся из `event.timeStamp`, плюс
сглаживание по времени (EMA, tau 30 мс).

Во-вторых, сама кривая. Даже с честной скоростью `1/speed` растягивает
измеренный диапазон 0.24-1.17 px/мс на flow от 1.40 до 0.85 — 60% разброса
внутри одного штриха, которого рука не просила. Описание настоящего
инструмента обратное: «линер почти всегда ложится плотно, за исключением
длинных быстрых штрихов». Это плато: фитиль метрирует чернила с темпом,
которым рука не управляет, и на всём диапазоне скоростей, на которых реально
штрихуют, подача успевает. Моделировать стоит только случай, когда кончик
обогнал подачу.

Тот же аргумент режет и медленный конец. Потолок 1.4 означал бы, что
медленный штрих кладёт на 40% больше чернил — но подача, которая «успевает»,
по определению уже отдаёт всё, что есть. Остаётся лёгкое подтекание на
несколько процентов. Полностью стоящий кончик к этой кривой не относится
вовсе: это `dwellFlow`, механизм по времени, у которого с #532 собственный
потолок (1.4) вместо общей с этой кривой константы — время на одной точке не
ограничено, скорость ограничена.

```
flow = 1.0                                   при 0.15 <= speed <= 1.75 px/мс
     -> 0.75 (smoothstep) к speed = 4.0      кончик обогнал подачу
     -> 1.05 (smoothstep) к speed = 0        подтекание ползущего штриха
```

См. `engine/src/linerPresets.ts`'s `linerSpeedFlow` — числа сверены с
измеренным диапазоном, но по-прежнему не проверены глазом на устройстве.

### 4. Впитывание бумаги (halo)

Два визуальных компонента: **core** (прямой контакт, почти непрозрачный,
геометрически стабильный) и **wicking** (узкий мягкий ореол вокруг,
зависящий от типа бумаги, сильнее на медленном движении/остановке, почти
отсутствует на Bristol/smooth).

v1: `wick = edgeMask * paperAbsorbency * dwellFactor` — без биаса вдоль
направления волокна (это even cheaper approximation, выглядит убедительно
без реальной жидкостной симуляции). Настоящий fiber-direction bias
(`localFiberBias`, чтение локального направления волокна из уже существующей
paper-grain карты) — explicitly deferred, см. «Потом» ниже.

**Важно, cross-device determinism (`.claude/rules.md`):** если halo будет
модулироваться существующей paper-grain текстурой (общий холст, должен
рендериться идентично у всех участников комнаты), сам эффект обязан
оставаться чисто функцией уже испечённых, детерминированных данных (paper
grain map, позиция даба) — не вводить новую live per-device GPU float
математику, к которой применимо всё то же предупреждение, что уже трижды
ловило регрессии на paper grain (см. `feedback`/`project_paper_grain_redesign`
и сам файл правил).

### 5. Насыщающийся композитинг

`newInk = oldInk + deposit * (1 - oldInk)` — уже соответствует тому, как
устроен текущий accumulation-blend (см. «Контекст» выше). Для линера просто
нужна кривая opacity/flow в пресете, где первый проход уже даёт почти
насыщенный чёрный, а второй в основном закрывает микропропуски бумаги, а не
удваивает плотность центра.

### 6. Старт и конец линии

- Без pressure-taper до нуля (нижний предел ширины даже при почти нулевом
  pressure — `widthPressure = lerp(0.94, 1.08, pressure)`), иначе цифровой
  линер превращается в каллиграфическое перо на отрыве стилуса. Тот же
  нижний предел для *depositGate* (не только ширины) теперь считается прямо
  в шейдере из настоящего, неусреднённого pressure — см. п.8's "Пересмотрено"
  примечание про то, почему это переехало из JS в GLSL.
- Быстрый отрыв → короткое сужение на 5–15%, не до нуля.
- **Dwell — реализовано как отдельный механизм, не "чуть более тёмная
  точка" (пересмотрено 2026-07-21, issue #245).** Изначально в v1 планировалось
  обойтись без настоящего накопления — считалось, что низкая скорость перед
  подъёмом уже даёт эффект через flow(speed). На практике этого недостаточно:
  `DabSystem` в принципе не порождает новых дагов, если указатель не сдвинулся
  (`continueStroke`'s >0.5px guard) — значит держать перо на месте буквально
  ничего не рисовало ни у одного инструмента. Добавлен таймер в движке
  (`PencilEngine._paintDwellDab`, `engine/src/linerPresets.ts`'s `dwellFlow`/
  `DwellConfig`/`dwellConfigForTool`) — пока стилус в пределах
  `stillThresholdPx` от точки, где остановился, раз в `intervalMs`
  подмешивается доп. даб в ту же позицию, с opacity по насыщающейся кривой от
  времени простоя (продолжение той же "constant flow over time" модели из
  п.3, взятой к пределу скорость→0). Общий, per-tool переключаемый механизм
  (`dwellConfigForTool`) — сейчас включён только для линера, но задел под
  Rapidograph/маркер уже есть.

### 7. Угол стилуса

`tilt < 55°`: почти без эффекта. `55–70°`: лёгкая эллиптичность (см. п.1).
`70°+`: небольшое снижение flow, возможны микропропуски — эффект
экстремального диапазона, не агрессивный на обычных углах письма.

### 8. Фактура и микропропуски

**Пересмотрено 2026-07-21 (issue #245), после QA v1.** Первая версия
(`coverage = contactMask * lerp(0.96, 1.0, paperContact) * flow`) сделала
реакцию на бумагу *независимой от нажима* — что при лёгком касании, что при
сильном, покрытие было одно и то же. Неправильно: у линера, как и у
графита, при слабом нажиме должно быть видно сырую фактуру бумаги почти как
есть, при сильном — плотнее, хоть и никогда не до конца, в отличие от
графита.

Возвращён pressure-зависимый fill (тот же механизм, что уже был у графита —
`effectiveCatch = mix(paperCatch, 1.0, fill)`), но с гораздо более слабым
cap (`LINER_FILL_CAP` в `shaders.ts`, первый проход — 0.55 против графитового
подхода к почти полной заливке): `paperContact = mix(paperCatch, 1.0,
smoothstep(0,1,pressure) * LINER_FILL_CAP)`. При pressure≈0 — почти сырой
`paperCatch` (текстура отчётливо видна), при pressure=1 бумага всё равно не
заливается полностью.

Важно: этот pressure должен быть **настоящим, неусреднённым** значением, не
уже применённым deposit-floor'ом из п.6 — иначе диапазон схлопывается и лёгкое
касание перестаёт отличаться от сильного (ровно так и было сломано в первой
версии, где deposit-floor был запечён в `Dab.pressure` на этапе записи). Из-за
этого deposit-floor из п.6 тоже переехал из JS (`DabShapingProfile.
depositPressure`) прямо в шейдер, считается там же, из того же настоящего
pressure, что и paperContact.

### 9. Пересечения и повторные проходы

Без wetness/времени высыхания в v1 — насыщающегося композитинга (п.5)
достаточно: центр пересечения почти не темнеет вдвое, край может слегка
расшириться из-за дополнительной жидкости.

## MVP-скоуп (Liner v1)

- Форма: почти круглый dab, ширина постоянна выше давления посадки и уходит
  к 0.6 при касании в ноль (п.1–2, пересмотрено #532), наклон даёт до 10–15%
  эллиптичности.
- Подача: constant-flow-over-time модель (п.3, пересмотрено #245 и #532) —
  плотно на всём рабочем диапазоне скоростей, светлее только на длинном
  быстром штрихе, saturating accumulation (п.5).
- Бумага: pressure-зависимый fill с гораздо более слабым cap, чем у графита
  (п.8, пересмотрено #245) — лёгкое касание показывает сырую фактуру, halo
  без волоконного bias (п.4).
- Начало/конец: без pressure taper в ноль; настоящий dwell-механизм на
  остановке — таймер в движке, не просто "чуть темнее" (п.6, реализовано
  #245).
- Наклон: п.7, без агрессивного поведения на обычных углах.
- Размеры: 0.1, 0.2, 0.3, 0.5, 0.8 мм — фиксированные шаги, свободный размер
  в advanced settings.
- Цвет: произвольный (переиспользование `ColorPicker`/`StrokeOperation.color`,
  как у Color pencil — см. `docs/TOOLSET.md`, «Пересмотр: два
  pencil-инструмента»), не только чёрный.
- Сглаживание траектории: переиспользовать текущую Catmull-Rom/corner-preserving
  систему `DabSystem` как есть — **не** добавлять искусственный jitter поверх
  хорошего стилуса; линия должна остаться чистой, но не выглядеть как
  vector-simplify-path.

## Потом (explicitly out of v1 epic, отдельные issues)

- Wicking вдоль направления волокна бумаги (`localFiberBias` из paper-grain
  карты, п.4) вместо простого halo.
- Износ наконечника (постепенное «размягчение» строгости линии).
- Отдельный Technical Pen / Rapidograph пресет (см. п.1, п.7) с фикс.
  калиброванными ступенями ширины 0.1–1.0мм.
- Wetness/время высыхания для более точного поведения при пересечении
  свежих линий (п.9).
- Звук инструмента (по аналогии с `PencilSound.ts`).

## Явно вне скоупа этого эпика

- Manga/G-pen (нажимное перо с сильной pressure→width кривой) и
  perspective/ellipse guide — обсуждались как соседние кандидаты в тулсет,
  сознательно не заводятся сейчас (см. `docs/TOOLSET.md`).
- Screentone — конфликтует с текущей анти-целью «без fill bucket», отдельное
  продуктовое решение, не бандлится с линером.
