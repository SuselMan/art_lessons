# ADR 006: Локализация интерфейса (i18n)

## Статус

Accepted (2026-07-27). Закрывает открытые вопросы эпика #208 и определяет,
как устроены переводы в `apps/web`. Первый заход — RU/EN; остальные языки
добавляются отдельной задачей поверх этой инфраструктуры.

## Контекст

Все строки интерфейса были захардкожены прямо в компонентах (в основном
по-английски, несколько описаний feature-флагов и один баннер — по-русски).
Инфраструктуры для переводов не было вообще.

Открытые вопросы, зафиксированные в #208 и решённые здесь: библиотека,
целевые языки, формат хранения строк, отношение к `packages/shared`, нужна ли
локализация серверных ответов.

## Решение

### Свой минимальный слой вместо библиотеки

`apps/web/src/i18n/` — около 150 строк кода, ноль новых зависимостей
(правило проекта: не добавлять зависимости без чёткой причины).

`react-i18next` был рассмотрен и отклонён. Он приносит i18next + плагинную
машинерию (namespaces, ленивая загрузка словарей, backend-плагины,
детекторы), из которой на этом проекте не нужно ничего: два языка, оба
собираются в бандл, детекция — три строки на `navigator.languages`.
Компенсации в виде `<Trans>` (JSX внутри предложения) тоже не требуется —
таких строк в UI нет.

Главный аргумент в пользу своего слоя — типизация. Ключи выводятся из
английского словаря (`keyof typeof en`), а остальные локали типизированы как
`Dictionary`, поэтому:

- вызов `t()` с несуществующим ключом — ошибка компиляции;
- ключ, добавленный в `en.ts` и не переведённый в `ru.ts`, — ошибка
  `npm run typecheck`, а не строка, которая тихо уезжает в прод
  по-английски.

С JSON-словарями i18next этого нет из коробки.

### Структура

```
apps/web/src/i18n/
├── types.ts      — PluralCategory / PluralForms / Message / TranslationParams
├── locale.ts     — Locale, LOCALES, LOCALE_NAMES, detectLocale (без React и без стора)
├── en.ts         — источник истины по набору ключей; отсюда выводится TranslationKey
├── ru.ts         — типизирован как Dictionary
├── translate.ts  — чистый lookup: словари, интерполяция, множественные числа
└── index.ts      — React-обвязка: useT() / useLocale() + реэкспорт
```

`translate.ts` намеренно не знает ни про React, ни про стор — это чистая
функция `(locale, key, params) => string`, поэтому тесты и не-компонентные
хелперы используют её без DOM. Подписка на выбранный язык живёт только в двух
хуках в `index.ts`.

Ключи — плоские, с namespace-префиксом по месту использования
(`room.`, `layers.`, `lessons.`, `tool.`, …). Плоская карта делает и lookup, и
вывод union-типа ключей, и проверку полноты локали тривиальными.

### Множественные числа

Через нативный `Intl.PluralRules`, а не через свою таблицу правил. Английскому
нужны две формы, русскому — четыре («1 слой / 2 слоя / 5 слоёв»); ни один из
наборов не захардкожен. Запись в словаре — объект форм, а не строка:

```ts
'layers.count': { one: '{n} слой', few: '{n} слоя', many: '{n} слоёв', other: '{n} слоя' }
```

Счётчик передаётся параметром `n`. На момент написания ни одна строка в UI не
зависит от числа — механизм заведён заранее и покрыт тестами именно потому,
что «английская» двухформенная реализация ломает русский на первой же такой
строке, и ломает молча.

### Данные, а не строки, в схемах

Реестры, которые описывают UI данными (`TOOL_SCHEMAS`, `HOTKEY_ACTIONS`,
`PRIMARY_TOOL_DISPLAY`, список размеров холста), хранят `TranslationKey`, а не
готовую подпись — язык выбирается в момент рендера. Значения enum-полей
переводятся выборочно, через `optionLabelKeys`: наконечник маркера и тип угля
— обычные слова и переводятся, а твёрдость карандаша (`HB`, `2B`) и толщина
линера (`0.3`) — международная маркировка и остаются как есть.

### Что не переводится

- **Dev-панели.** Список feature-флагов, селекторы вариантов зерна, панель
  тюнинга звука, debug-оверлеи — внутренние инструменты, которые меняются
  вместе с тем, что ими исследуют. Их перевод — постоянная лишняя работа при
  нулевой пользе. Вкладка «Горячие клавиши» и обвязка панели настроек — это
  настоящая пользовательская функция, и они переведены.
- **Пользовательский контент.** Имена слоёв, названия комнат и папок едут
  через Operation Log ко всем участникам. Слой, созданный в русском
  интерфейсе, называется «Слой 3» и для англоязычного участника тоже — это
  общий контент, а не локальный чром, и вести себя иначе он не должен.
- **`packages/shared`.** Лексика выбора бумаги переехала в словарь веба, а не
  осталась в `PAPER_*_LABELS`. `shared` — контракт между фронтом и бэком, а не
  место для переводов одного клиента.
- **Ответы сервера.** Сервер отдаёт код причины (`not_found`,
  `invalid_credentials`, `cycle`, `not_empty`), а не готовый текст; клиент
  превращает код в предложение на своём языке. Это уже было так — решение
  лишь зафиксировано явно, и локализация сервера отдельной задачей не нужна.

### Хранение выбора языка

`apps/web/src/stores/settingsStore.ts` — отдельный zustand-стор для настроек
уровня приложения, ключ `al_locale` в localStorage.

Отдельный от `roomStore` намеренно, хотя в проекте принято держать один
глобальный стор: `resetRoomStore()` заменяет всё состояние при каждом
монтировании Room, то есть язык сбрасывался бы при каждом входе в комнату.
Настройки человека переживают любую комнату, и им нужен контейнер, который
никогда не сбрасывается. Тема и подобное поедут сюда же.

При первом заходе язык определяется по `navigator.languages` (совпадение по
первому сабтегу: `ru-RU`, `ru-BY` и `ru` → `ru`). Как только выбор сохранён,
смена языка браузера его больше не перебивает. Переключение применяется
сразу, без перезагрузки: `useT()` — это подписка на стор.

## Последствия

- Добавление языка = один файл `<locale>.ts`, типизированный как `Dictionary`,
  плюс строка в `LOCALES`/`LOCALE_NAMES`. Компилятор перечислит всё, что не
  переведено.
- Добавление строки = ключ в `en.ts`; сборка не пройдёт, пока он не переведён
  во всех локалях.
- Словари попадают в основной бандл целиком. При двух языках это несколько
  килобайт; если языков станет заметно больше, точка расширения — динамический
  `import()` словаря в `translate.ts`, без изменений в компонентах.
