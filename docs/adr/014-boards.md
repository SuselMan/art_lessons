# ADR 014: Доски — несколько холстов в одном уроке

## Статус

**Принято**, эпик #176, релиз-трек #314 §11.

Заведено 16.07 как «архитектурное обсуждение до реализации» и вынесено из трека.
23.09 Илья вернул: на живых уроках не хватает возможности «перевернуть страницу» —
продолжить объяснение на чистом листе, не выгоняя всех в новую комнату. Признано
блокером релиза, здесь — модель.

---

## §1. Контекст

Сейчас комната = урок = один набор слоёв. У `Room` две группы данных, склеенные одним
id:

- **социальное**: участники (`RoomParticipant`), инвайты, заявки на вход, блокировки,
  пароль, `accessMode`, `closedAt`, `enabledTools`, живой freeze (комнаты и участника),
  папка в «Моих уроках»;
- **содержимое**: лог операций (`Operation`, `@@unique(roomId, seq)`), снапшоты слоёв,
  `RoomLayerState`, превью, бумага и размер холста.

Доска — это разделение этих двух групп: один социальный контур на урок, N независимых
содержимых. Аналог — boards в Magma и страницы в Procreate.

Что уже есть и на что опираемся:

- `Room.parentRoomId` — **занято домашкой** (#317): «откуда скопировано». Форк ученика и
  доска учителя должны быть различимы, поэтому доске нужна своя ссылка на урок.
- `join_room` уже умеет «переключить» сокет: если сокет был в другой комнате, сервер сам
  делает `leaveRoom` и `peer_left` старой (`socketHandlers.ts`, ветка implicit leave).
  Отдельного `leave_room` нет, клиент сейчас держит по сокету на комнату.
- Страница `/room/:id` **не размонтируется** при смене id (`Room/index.tsx`, комментарий у
  #358): `resetRoomStore()` зовётся один раз через `useState(resetRoomStore)`, а эффекты
  движка и сокета зависят от `id` и перезапускаются.
- Форк (`forkRoutes.ts`) — готовая процедура «засеять новую комнату содержимым другой»:
  последний снапшот на слой + хвост операций с перевыписанными id.
- Серверный реестр `rooms.ts`: `Map<roomId, RoomRecord>`, запись держит и социальное
  (participants, roomFrozen, frozenUserIds), и содержимое (operations, layerState,
  nextSeq). Эвикция — когда запись пуста и записи в БД слиты.

## §2. Решение: доска — это `Room` с `lessonId`

**Урок = существующая `Room`, и она же — первая доска.** Дополнительные доски — строки
`Room` с новой колонкой `lessonId`, указывающей на урок. Всё существующее — уроки с одной
доской, миграция данных не нужна.

```prisma
model Room {
  // ...
  lessonId      String?   // null = это урок (и его первая доска)
  lesson        Room?     @relation("LessonBoards", fields: [lessonId], references: [id], onDelete: Cascade)
  boards        Room[]    @relation("LessonBoards")
  boardOrder    Int       @default(0)   // позиция в ленте; у урока всегда 0
  activeBoardId String?   // доска, на которой учитель; null = сам урок
  @@index([lessonId, boardOrder])
}
```

Одно правило резолва, сквозное для сервера: **`lessonOf(room) = room.lessonId ?? room.id`**.
Всё социальное читается и пишется у `lessonOf`, всё содержимое — у самой доски.

| Что | Живёт на | Как резолвится |
|---|---|---|
| участники, инвайты, заявки, блоки, пароль, `accessMode` | урок | `checkJoinAccess(board)` → проверяет `lessonOf(board)` |
| `closedAt`, `enabledTools`, палитра | урок | `getOperationRejectReason`, `set_room_tools`, `palette_*` ходят к записи урока |
| freeze комнаты и участника | запись урока в памяти | `roomFrozen`/`frozenUserIds` берутся у записи урока |
| папка, имя карточки, владелец | урок | доски (`lessonId != null`) **никогда** не попадают в списки: `GET /api/rooms`, `/search`, `/mine` фильтруют `lessonId: null` |
| лог операций, `nextSeq`, снапшоты, `RoomLayerState` | доска | как сейчас, по id доски |
| превью | доска | карточка урока показывает превью `activeBoardId ?? lesson` |
| бумага, цвет, `infinite`, размер | доска | наследуются от урока при создании (как в форке); смена размера у доски — не в MVP |
| имя доски | доска | `Room.name`; у урока `name` — имя урока и первой доски одновременно |

Глубина ровно один: у доски `lessonId` указывает на комнату с `lessonId = null`. Сервер
отвергает создание доски внутри доски.

### Почему не отдельная таблица `Lesson`

Все социальные таблицы уже висят на `Room` с `onDelete: Cascade`, и все REST-маршруты
доступа (`/invites`, `/blocks`, `/join-requests`, `/close`) принимают `:roomId`. Вынос
социального в новую сущность — миграция каждой из этих таблиц и каждого маршрута ради
того же результата. `lessonOf` даёт то же разделение одной функцией.

### Почему не `boardId` в таблицах содержимого

Второй вариант из #176: оставить одну комнату и добавить `boardId` в `Operation`,
`RoomLayerSnapshot`, `RoomLayerState`, `RoomThumbnail`. Это правка каждого пути записи и
чтения содержимого, реплея, компакции, снапшотов и форка — и всё это уже работает по
`roomId`. Доска-как-комната получает undo, реплей, снапшоты, превью и границы холста
(#469) даром.

## §3. Сокет: один на урок, канал урока + канал доски

Клиент держит **один сокет на урок**, а не на комнату. Сервер держит сокет в двух
socket.io-каналах: `lessonId` для социального и `boardId` для содержимого.

| Канал | Что летит |
|---|---|
| `io.to(lessonId)` | `peer_joined`, `peer_left`, `peer_board_changed`, `room_frozen_changed`, `participant_frozen_changed`, `room_tools_changed`, `room_closed_changed`, `palette_updated`, `active_board_changed`, `board_created` / `board_renamed` / `board_deleted` / `boards_reordered` |
| `io.to(boardId)` | `operation_confirmed`, `peer_stroke_live` / `_end`, `peer_cursor` |

Переключение доски — это существующий `join_room { roomId: boardId }` на том же сокете.
Сервер: доступ через `lessonOf`, `socket.leave(oldBoardId)`, `socket.join(boardId)`,
`room_state` доски, `peer_board_changed` в канал урока. Сокет остаётся в канале урока.
Отдельный `switch_board` не заводим: `join_room` уже делает implicit leave, а второй
путь входа — второе место для гейтов доступа.

`room_state` доски дополняется полем `lesson`: `{ id, boards: BoardSummary[], activeBoardId }`,
где `BoardSummary = { id, name, order, thumbnailUpdatedAt? }`. Участники в `room_state` —
участники **урока**, у каждого `boardId`.

### Ведущий и следование

`activeBoardId` — доска учителя. Учитель здесь = владелец урока (единый teacher-флаг #90
расширит это позже, модель не мешает).

- Владелец шлёт `set_active_board { boardId }` → сервер пишет `Room.activeBoardId` в БД и
  шлёт `active_board_changed` в канал урока. Персистится, чтобы вход и перезагрузка
  попадали на доску учителя.
- Клиент в режиме **следования** (по умолчанию) на `active_board_changed` переключается
  сам. Ученик, выбравший другую доску руками, из следования выходит и видит чип
  «учитель на доске N» — тап по нему возвращает на доску учителя и включает следование
  обратно. Владелец никогда не «следует».
- Вход в урок (`/room/:lessonId`) — на `activeBoardId ?? lessonId`.

Раздельный просмотр без ведущего (каждый где хочет, молча) на уроке не нужен и
противоречит манифесту §5 («все видят одно полотно») — но модель его не запрещает,
ученик просто не следует.

### Права

- Создать, переименовать, удалить, переставить доски — владелец урока. Удалить первую
  доску (сам урок) нельзя.
- Удаление доски — жёсткое, cascade-удаление строки со всем содержимым. Восстанавливать
  некуда, поэтому клиент спрашивает подтверждение, как «Очистить холст» после #171.
  Мягкое удаление не заводим: восстановление по версиям комнаты — отдельная отложенная
  тема, и доска в неё войдёт вместе со всем остальным.
- Рисовать на любой доске может любой, кто может рисовать в уроке: гейты freeze, lock,
  `closedAt`, `enabledTools` — у урока.

### Реестр в памяти

`RoomRecord` урока держит участников (каждый с `boardId`), freeze, палитру. `RoomRecord`
доски держит содержимое и **множество сокетов на ней** — по нему доска эвиктится, когда
на ней никого нет, даже если урок жив. Запись урока живёт, пока в уроке есть хоть один
сокет, потому что её первая доска и социальное состояние нужны всем. `admitRoomLoad`
(гейт по памяти) считает каждую доску отдельной загрузкой — это честно, доска и есть
отдельный набор слоёв.

## §4. Клиент: сокет по уроку, движок по доске

Страница остаётся `/room/:id`, где `id` — **урок**. Board id в URL не кладём: куда попасть
на входе решает `activeBoardId`, а deep link на доску не нужен. Если в URL приехал id
доски (кто-то скопировал из превью-запроса) — сервер отдаёт `lessonId` в `room_state`,
клиент делает `navigate('/room/<lessonId>', { replace: true })` и выбирает эту доску.

В сторе (`roomSlice`) добавляются `boardId`, `boards`, `activeBoardId`, `following`.
Эффекты страницы делятся по ключу:

| Эффект | Ключ сейчас | Ключ станет |
|---|---|---|
| сокет (`io()`, `join_room`, обработчики) | `id` | `lessonId` — один на урок |
| движок (`new PencilEngine`, снапшоты, превью при размонтировании) | `id` | `boardId` |
| загрузка снапшотов по HTTP | `id` | `boardId` |

Переключение = `setBoardId(next)`: сбрасываются content-слайсы (`layerSlice`,
`viewportSlice`, `strokeSlice`, `selectionSlice`, `annotationSlice`), **не** сбрасываются
`roomSlice` и `toolSlice` (инструмент, пресет и цвет «в руке» переживают перелистывание —
так ведёт себя бумага). Это отдельный `resetBoardState()`, а не `resetRoomStore()`.
Cleanup старого движка отправляет превью доски, как сейчас при выходе из комнаты, затем
`join_room(nextBoardId)` на живом сокете, затем HTTP-загрузка снапшотов новой доски.

Outbox (#202, очередь неподтверждённых операций) — per-board: операции адресованы доске,
и переключение с непустым outbox ждёт его слива, как сейчас ждёт #358 при смене id.

Undo-стек клиента живёт в движке и умирает с ним. После возврата на доску undo
начинается с чистого листа. Это принятое ограничение MVP: восстановить стек можно из
хвоста лога (ADR 002, undo адресует операции по id), но это второй шаг.

## §5. Форк и шаблоны

Две точки форка уже различаются в UI (#222/#317), различие переносится на доски:

- **«Взять в работу»** изнутри закрытой комнаты — форк **текущей доски** в самостоятельную
  комнату (`lessonId: null`). Ученик работает над тем листом, который видел.
- **«Форк» из «Моих уроков»** — форк **всего урока**: копируется урок и каждая его доска,
  у копий досок `lessonId` указывает на новый урок, `activeBoardId` перемапливается.
  Это и есть заготовка шаблона урока (#107): «куб», «цилиндр», «конус» подготовлены по
  доскам, учитель форкает урок и ведёт занятие. Право — участник источника, как сейчас.

Процедура засева одной комнаты (`forkRoutes.ts`) по результату не меняется, форк урока —
цикл по ней в одной транзакции. По механизму изменилась в #568: лог операций копируется
внутри Postgres одним `INSERT … SELECT` на чанк, id новой операции — `md5(sourceId + forkId)`,
считается одинаково на обеих сторонах; в JS читаются и перемапливаются только undo/redo/revoke.
Без этого пять досок по 2000 штрихов упирались в 30-секундный таймаут транзакции (27.9 с),
с этим — 1.8 с, десять досок по 5000 штрихов — 11.4 с, линейно.

## §6. Что это стоит и что откладываем

- **Цена возврата на старую доску** — та же, что вход в комнату: снапшоты по HTTP (#425,
  вход тянет ~13 МБ). «Дальше на чистом» быстро, доска пуста. Кэш последних досок в
  памяти клиента — второй шаг, после того как #425 уменьшит сам объём.
- **Undo после возврата** — см. §4.
- **Размер и бумага доски** наследуются от урока; своя бумага на доску — не в MVP.
- **Вложенность** — один уровень, проверяется сервером.
- **Датасет (#375)**: лог по-прежнему полный, теперь по доске. Ничего не теряется.
- **Мобильная оболочка аннотаций (#512)** — аннотации per-board, так как реплеятся из
  лога доски; лента досок в телефоне — только просмотр.

## §7. Разбиение

Порядок — снизу вверх, каждый шаг проверяем отдельно:

1. Shared + Server: схема (`lessonId`, `boardOrder`, `activeBoardId`), `lessonOf` во всех
   гейтах доступа, `closedAt`, freeze, tools, палитре; списки и поиск прячут доски;
   REST-маршруты содержимого (`/snapshots`, `/thumbnail`) принимают id доски и проверяют
   доступ через урок; маршруты доступа (`/invites`, `/blocks`, `/join-requests`, `/close`)
   на id доски отвечают 404.
2. Server: сокет — `join_room` доски держит сокет в двух каналах, участники урока с
   `boardId`, `peer_board_changed`, `set_active_board` / `active_board_changed`, REST
   CRUD досок (`POST/PATCH/DELETE /api/rooms/:lessonId/boards`) с broadcast, эвикция
   доски по пустому множеству сокетов.
3. Web: стор и страница — `boardId`/`boards`/`activeBoardId`/`following`,
   `resetBoardState()`, движок и HTTP-загрузка по `boardId`, сокет по `lessonId`,
   переключение с ожиданием outbox, редирект с id доски на урок.
4. Web UI: лента досок — кнопка в верхней панели, полоса превью с именами, «+» и меню
   (переименовать, удалить с подтверждением, переставить) у владельца, чип
   «учитель на доске N» у отставшего ученика; на тач с minimal UI прячется вместе с
   шапкой. Карточка в «Моих уроках» показывает превью активной доски.
5. Форк урока целиком из списка (все доски, `activeBoardId` перемаплен); «взять в
   работу» форкает текущую доску.
6. e2e: учитель создаёт вторую доску → ученик следует → оба рисуют → учитель возвращается
   на первую → содержимое обеих досок на месте у обоих → перезагрузка ученика попадает
   на доску учителя.
