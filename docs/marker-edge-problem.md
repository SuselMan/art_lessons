# Маркер: как устроен сейчас и в какую стену мы упёрлись

## Контекст

Веб-приложение для рисования (совместный холст, учитель + ученики). Движок свой, **WebGL1**
(без WebGL2-фич), рендер только на клиенте. Каждое действие сериализуется в Operation Log:
сервер ретранслирует операции, но ничего не рендерит — итоговые пиксели каждый участник
пересчитывает у себя, воспроизводя тот же лог. Отсюда жёсткое требование: результат не должен
зависеть от особенностей конкретной GPU (уже трижды обжигались на этом с текстурой бумаги —
`precision highp float` во фрагментном шейдере это *просьба*, а не гарантия, и на мобильных
GPU молча падает в mediump).

Холст тайловый, буферы слоёв — RGBA8 (8 бит на канал), премультиплицированные.

## Общая механика штриха (общая для всех инструментов)

1. Точки пера собираются в центростремительный сплайн Catmull-Rom (α=0.5), с отставанием на
   одно событие ради C1-непрерывности.
2. Вдоль сплайна с равным шагом по длине дуги расставляются **дабы** (отпечатки):
   `spacing = max(1px, baseSize * 0.22)`.
3. Каждый даб — четырёхугольник (quad), растянутый по локальной оси X на `aspectRatio` и
   повёрнутый на `angle`. Внутри фрагментного шейдера:

```glsl
// v_localUV — это a_position * 2, т.е. −1..1 поперёк уже растянутого квада
float dist = length(v_localUV);          // 1.0 = граница даба
if (dist > 1.0) discard;

float innerEdge = u_hardness * 0.85;
float shape = 1.0 - smoothstep(innerEdge, 1.0, dist);
shape *= 1.0 - exp(-8.0 * (1.0 - dist));  // дополнительное смягчение у самого края
```

`shape` — это и есть профиль отпечатка: 1 в середине, 0 на границе.

## Как устроен именно маркер

Наконечника два: **bullet** (почти круглый, aspect 1.0–1.15 от наклона пера) и **chisel**
(плоское перо, фиксированный **aspect 5:1**, угол — настройка пользователя, по умолчанию 45°,
опционально следует направлению штриха). Размер кисти в UI: 1–120 px, по умолчанию chisel.

Отклик на нажим намеренно слабый (войлочный наконечник не сжимается как графит): ширина
0.94–1.08, поток краски 0.85–1.15. Есть отклик на скорость и наклон, есть «лужица» при
остановке пера (dwell).

Композитинг — не обычный «over», а **умножение** (краситель на бумаге, Beer-Lambert). На каждый
даб идут три прохода в отдельные буферы:

1. **coverage** — силуэт мазка. Обычный насыщающийся «over»-сплат:
   `amt = shape * opacity * 1.4` (последний множитель — недавняя правка, см. ниже),
   плюс небольшой краевой подтёк по бумаге `(1-shape) * (1-dist) * (1-paperCatch) * 0.35`.
2. **inkLoad** — сколько краски реально положено. Копится **аддитивно**, без потолка,
   величиной `dab.opacity * segmentLength` (нормировка по пройденному расстоянию, чтобы
   количество краски зависело от длины штриха, а не от числа дабов).
3. **composite** — собственно пиксель. Читает «замороженное» содержимое тайла до начала мазка
   (`original`), и:

```glsl
vec3 base = un-premultiply(original);           // vec3(1.0) там, где пусто
float layer1 = smoothstep(0.0, 0.6, inkLoad);
float layer2 = smoothstep(0.0, 1.2, max(inkLoad - 0.6, 0.0));
vec3 afterLayer1 = mix(base, base * u_color, layer1);
vec3 result      = mix(afterLayer1, afterLayer1 * u_color, layer2);   // ровно два слоя, дальше стоп
float newAlpha   = mix(original.a, 1.0, coverage);
```

Идея двух дискретных слоёв: первый проход по чистому месту читается ровно как выбранный цвет,
второй — как второй слой той же плёнки (`color * color`), третий и далее ничего не меняют.
Это осознанное требование заказчика: не бесконечное сползание в чёрное, а жёсткий потолок.

Ключевое: **composite — не инкремент, а полный пересчёт пикселя** из (original, coverage,
inkLoad). Поэтому он пишется в тайл с выключенным блендингом (перезапись).

## Что мы только что чинили

Жалоба была: «на большой кисти штрих распадается на отдельные прямоугольники». Нашли три
независимые причины, все починили:

1. **Композит смешивался «over» вместо перезаписи.** Полный идемпотентный пересчёт, сложенный
   сам с собой, компаундил альфу (`A = a + A(1-a)`) — пиксель внутри N отпечатков проходил N
   композиций, соседний N−1, на границе каждого отпечатка возникала ступенька до 53/255.
2. **Краевой подтёк обрывался на границе даба.** Член `(1 - shape)` *растёт* к краю и жёстко
   обрубался `discard`-ом — скачок ~0.08 в coverage вокруг каждого отпечатка (20/255).
3. **Главное: даб с aspect > 1 был буквально прямоугольником.** В шейдере стояло
   `uv.x = v_localUV.x / max(aspect, 1.0)` — деление на aspect *второй раз*, при том что
   вертексный шейдер уже растянул квад. Контур спада уезжал на `aspect² × radius`, а геометрия
   кончалась на `aspect × radius`, поэтому вдоль длинной оси спада не происходило вообще:

```
вдоль длинной оси, от центра к краю квада (chisel 5:1, радиус 40px):
было:  1.00 1.00 1.00 1.00 1.00 1.00 1.00 1.00 1.00 1.00 1.00   ← прямоугольник
стало: 1.00 1.00 1.00 1.00 0.99 0.98 0.95 0.73 0.37 0.08 0.00   ← эллипс
```

Прямоугольники ушли. Но вылезло то, что этот баг маскировал.

## Проблема, ради которой пишем

**Край маркера стал слишком размытым.** И это не вопрос подкрутки константы: ширина размытия
у нас **пропорциональна размеру кисти**, тогда как у настоящего маркера она физическая
константа.

Причина прямо в формуле: `shape` определён в *нормализованном* пространстве даба, где граница
всегда `dist = 1`. Полоса спада `[hardness*0.85, 1]` — это фиксированная доля радиуса, то есть
в пикселях она растёт вместе с кистью. А по длинной оси она ещё и умножается на aspect.

Измерения (наши реальные формулы, ширина спада 90%→10%):

| один отпечаток | поперёк пера | вдоль пера |
|---|---|---|
| bullet, радиус 8px | 1.7px | 1.7px |
| bullet, радиус 40px | 8.6px | 8.6px |
| chisel, радиус 8px | 2.0px | 10.2px |
| chisel, радиус 40px | 10.2px | **51.0px** |

| готовый прямой штрих | полуширина мазка | спад 90→10% | доля |
|---|---|---|---|
| bullet, радиус 8px | 6.2px | 2.2px | 36% |
| bullet, радиус 40px | 31.3px | 11.2px | 36% |
| chisel 45°, радиус 8px | 21.8px | 8.8px | 40% |
| chisel 45°, радиус 40px | 108.6px | **43.9px** | 40% |

То есть **край всегда занимает ~36–40% полуширины мазка, каким бы ни был размер кисти.**
На кисти 120px (максимум в UI) это десятки пикселей градиента. Реальный маркер так себя не
ведёт: у войлочного/спиртового наконечника граница резкая и её ширина не зависит от того,
взяли вы тонкий маркер или широкий — это свойство наконечника и впитывания бумаги, а не
масштаба.

Поднять `hardness` до предела не спасает: множитель `1 - exp(-8*(1-dist))` сам по себе даёт
мягкий ободок шириной ~29% радиуса, и он тоже в нормализованных единицах.

## В чём мы видим настоящий конфликт

Наивное решение — сделать спад фиксированным в экранных пикселях (1–2px антиалиасинга плюс
маленький подтёк по бумаге). Но тут вылезает то, ради чего мягкий край, похоже, и существовал:

Мазок собирается из **штампов, наложенных с шагом 0.22 × размер кисти**. Объединение
перекрывающихся эллипсов имеет фестончатую (гребёнчатую) границу. Пока край мягкий, фестоны
тонут в градиенте. Сделаем край резким — фестоны станут видны как зубцы, и мы вернёмся к
исходной жалобе, только в другой форме.

Формулируя честно: **штамповая модель прячет зубчатость объединения за размытием, ширина
которого обязана расти вместе со штампом. Маркеру нужна резкая граница постоянной ширины.
Эти два требования в текущей архитектуре несовместимы.**

## Направления, которые мы рассматриваем (и по которым нужен совет)

1. **Считать границу как SDF заметённой фигуры, а не штамповать.** На сегмент сплайна —
   один quad, во фрагменте считать расстояние до объединения (сумма Минковского эллипса
   наконечника с отрезком пути), край — 1px аналитического AA. Математически точное
   объединение, зубчатости нет в принципе, резкость не зависит от размера. Цена — переписать
   растеризацию маркера целиком, и для chisel это SDF повёрнутого эллипса, заметённого по
   отрезку (замкнутой формулы нет, нужна аппроксимация).

2. **Оставить штампы, но собирать силуэт через `max`, а не через «over».** `max` идемпотентен
   и не зависит от порядка, поэтому объединение штампов получается точным, и каждый штамп
   можно рисовать с резким краем и аналитическим AA. В WebGL1 это `EXT_blend_minmax`
   (расширение; в WebGL2 — ядро). Правка небольшая.

3. **Разделить «геометрию» и «плотность красителя».** Сейчас `coverage` тащит на себе и
   силуэт, и прозрачность мазка. Возможно, физичнее: alpha = (геометрическое покрытие с 1px AA)
   × (непрозрачность плёнки от inkLoad), а вся полупрозрачность лёгкого касания живёт в
   умножении цвета, а не в мягкости края. Тогда край может быть резким, не делая мазок
   непрозрачным.

# Ответ эксперта: что проверено и что решено (2026-07-28)

Эксперт рекомендовал не прыгать в полноценный SDF-sweep, а рендерить **соединённую ленту**
(контур наконечника вдоль пути: caps + bridges), задавать AA в пикселях **холста**, разделить
геометрическое покрытие и плотность красителя, и заменить эллипс 5:1 на rounded box.

Два его утверждения проверены на наших числах.

## 1. Фестоны: подтверждено, и это решает выбор архитектуры

Отклонение силуэта из штампов от истинной заметённой фигуры:

| конфигурация | spacing 26.4px (сейчас) | 8px | 4px | 2px | 1px |
|---|---|---|---|---|---|
| bullet, R=60 | 1.46px | 0.13px | 0.03px | 0.01px | 0.00px |
| chisel 5:1 @45°, R=60 | **20.84px** | 6.16px | 3.05px | 1.51px | 0.75px |
| rounded box 5:1 @45°, R=60 | **26.26px** | 7.98px | 3.98px | 1.98px | 0.98px |

Для круглого наконечника отклонение падает квадратично — spacing 8px закрывает вопрос.
Для chisel оно падает **линейно**, с коэффициентом ≈ sin(угла пера) ≈ 0.75, потому что плоское
перо смещается целиком. Чтобы уложиться в допуск 0.5px, нужен spacing ≈ 0.7px — около 1400
дабов на штрих в 1000px. Вариант «просто уменьшить spacing» не работает не только по
производительности, но и по качеству.

**Вывод: лента для chisel — не оптимизация, а единственный путь.**

Поправка к рекомендации эксперта: rounded box **усиливает** фестоны (26 против 21 при том же
spacing), потому что плоская грань двигается вся сразу. Менять форму наконечника до внедрения
ленты нельзя — станет хуже. Только вместе с ней.

## 2. Потолок в два слоя между мазками: подтверждено, но принято как есть

Эксперт прав: потолок работает только внутри одного мазка. Каждый мазок получает свежий
`MarkerStrokeScratch`, `original` — содержимое тайла на момент начала мазка, `inkLoad`
обнуляется. Второй мазок берёт `base = color²` и умножает снова.

**Решение Ильи (28.07): оставляем как есть.** Глобальный потолок требует持оянного per-pixel
состояния пигмента на слое — это заметная память на тайл, а осознанно накладывать маркер
слоями почти никто не будет. Формулировка в коде исправлена, чтобы это перестало выглядеть
багом.

## 3. По детерминизму — принято частично

Квантизация всех геометрических величин и LUT для оптической формулы отложены. Источник наших
прошлых расхождений между GPU был не в этом: op log хранит у всех одинаковые значения, горели
мы на усилении finite-difference внутри шейдера. Coverage по интерполированному атрибуту такого
класса риска не несёт. `fwidth`/`dFdx` не используем — согласны, но потому что это расширение
WebGL1 и источник межвендорной разницы.

## 4. Чего эксперт не упомянул: AA-швы внутри ленты

Если сглаживать все рёбра примитивов, на внутренних стыках (cap ↔ bridge) получаются волосяные
линии: 0.5 и 0.5 с обеих сторон общего ребра не дают 1. Сглаживать нужно **только внешний
контур**, внутренние стыки оставлять сплошными и дать примитивам перекрываться, чтобы AA-край
одного попадал внутрь сплошной области соседнего.

Здесь же выясняется, зачем всё-таки нужен `max`-блендинг: не как замена ленте (эксперт прав,
фестоны он не убирает), а как **оператор объединения** для её примитивов — при `max` AA-граница
cap'а, проходящая внутри bridge'а, где покрытие уже 1, ничего не портит.

# План

## Этап 2 — лента (принят к работе)

1. Покрытие (силуэт) считается по геометрии, а не по штампам:
   - контур наконечника (cap) в каждом sample — аналитический SDF в локальных координатах;
   - bridge между соседними sample'ами — квад по опорным точкам наконечника, расстояние до
     внешней границы идёт интерполированным атрибутом (точно для прямого участка);
   - объединение через `max` (`EXT_blend_minmax`, с запасным путём на saturating over).
2. AA фиксированной ширины в пикселях холста (~1px), нормализованный профиль убран.
3. `coverage` отвечает только за силуэт, `inkLoad` — только за плотность, как и было задумано.
4. Композит перестаёт быть per-dab: один проход по грязному прямоугольнику пачки дабов на тайл.
5. Всё за дев-флагом, чтобы сравнивать со старым растеризатором А/Б.

## Этап 3 — качество

1. Адаптивный sampling по кривизне пути и скорости изменения угла пера.
2. Форма наконечника: rounded box вместо эллипса 5:1 (только после п.1 этапа 2).
3. Бумажный край возвращается отдельным слабым эффектом поверх резкой границы.

## Не делаем

- Глобальный потолок слоёв между мазками (решение выше).
- Полноценный SDF заметённой фигуры.
- Квантизацию геометрии и LUT оптической формулы.

# Реализовано (2026-07-28): этапы 2 и 3

## Что изменилось

**Силуэт.** Маркер больше не собирается из независимых отпечатков. В каждом sample рисуется
контур наконечника, между соседними — полоса (band), построенная по опорным точкам. Для
выпуклой фигуры сумма Минковского с отрезком равна выпуклой оболочке двух её копий, поэтому
`отпечаток ∪ полоса ∪ отпечаток` — это **точно** заметённая фигура, без приближений.

**Край.** Задаётся расстоянием в пикселях холста, а не в долях радиуса: `MARKER_EDGE_AA_PX = 1.0`.
Отпечаток считает аналитический знаковый SDF (эллипс — оценка первого порядка `(f-1)/|∇f|`,
скруглённый прямоугольник — точная формула), полоса — интерполированный по вершинам атрибут.
Рампа односторонняя, внутрь от границы, у обоих примитивов одинаково — поэтому там, где они
стыкуются, они дают одно и то же значение.

**Форма chisel.** Скруглённый прямоугольник вместо эллипса 5:1, скругление 0.28 от короткой
полуоси. Стало возможным только с лентой: как форма *штампа* прямоугольник был хуже эллипса.

**Краска.** Отдельный проход с той же геометрией, что и силуэт (было: мягкий профиль, спадающий
до нуля). Ослабление к краю — 0.9, а не 0 → 1: маркер под слабым нажимом должен становиться
бледнее, а не превращаться в аэрограф. Пик в центре не изменился, так что калибровка
`MARKER_LAYER*_INK` осталась валидной.

**Композит.** Один проход на пачку дабов по её грязному прямоугольнику вместо прохода на даб.
Он всегда был чистым пересчётом из (original, coverage, inkLoad), а теперь coverage дотягивается
между дабами, и поквадратный проход перестал бы покрывать написанное.

**Sampling.** Адаптивный, но только по кривизне и только у маркера
(`DabSystem.curvatureTolerancePx = 0.5px`). Перенос лента передаёт точно, поэтому осталась одна
ошибка — хорда вместо дуги, сагитта `s²κ/8`. Она и так меньше пикселя почти везде (0.87px для
кисти 120px на радиусе 100px), заметна только в углу пространства «очень широкая кисть на очень
крутом повороте» (2.9px при радиусе 30px) — там шаг и уплотняется.

## Результат (та же модель, что мерила проблему)

chisel 5:1 под 45°, кисть 120px, spacing 26.4px:

| | было | стало |
|---|---|---|
| спад края 90→10% | 43.9px | **0.80px** |
| размах альфы вдоль штриха (фестоны) | 20.8px геометрии | **0.0/255** |

Ширина края больше не зависит от размера кисти — это её свойство по построению, а не результат
подбора.

## Отложено осознанно

**Бумажный край** (мягкий подтёк по шероховатости бумаги отдельным слабым эффектом). Причина:
жалоба была ровно на избыточную мягкость края, а вернуть подтёк вслепую — значит снова добавить
размытие, не видя результата. Возвращать после того, как резкость подтверждена глазами; шкала
из ответа эксперта — 0.3–0.8px на гладкой бумаге, 0.8–2.0px на грубой.

## Как сравнить со старым

Дев-флаг **«Маркер: старый штамповый растеризатор»**. По умолчанию выключен, то есть работает
лента. Старый путь целиком сохранён и покрыт тестами — но он существует только ради сравнения
и должен быть удалён, как только сравнение проведено.
