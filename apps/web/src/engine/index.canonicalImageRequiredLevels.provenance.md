## CPU ownership and synchronous lifetime proof

No new requirements arrays are retained in admission/accepted/candidate plans or
across jobs/yields. The private lexical consumer is type-closed to synchronous
number/boolean/bank/extension/budget results (no Promise/array return), and visitor
returns undefined. It additionally rejects a then-bearing result without reading
its property. All actual callbacks synchronously consume/copy requirements into
existing bank jobs/budget metadata or return a scalar. It never passes requirements
to a user callback or closure for deferred work.

Each invocation reserves through the SAME BrushMipCache owner before new live data:
-512B before seen/merge map headers;
-128B per seen original material identity before retaining it in the lexical map;
-16384+1536*actualAssetCount before pin/requirement capture. Validated dimensions
 <=4096 imply fewer than32 original pyramid levels. This conservative workspace
 covers bounded copied asset/index data plus one transient pyramid metadata array;
-1024B per actually merged full asset/crop before retaining asset/key/first/last/
 release token. No new key is retained before its reservation;
-128+512*actualMergedCount+16*actualIndexCount before materializing the final list.

Seen<=1024, unique assets<=256, selected original jobs<=4096; existing16/4MiB caps
are unchanged. Map/array merges and overlap are therefore charged by each actual
lexical call, not an assumed four copies. Reentrant calls get their own reservations
and can fail the same CPU cap; there is no global registry or new allowance.
Finally retires map entries before release callbacks and attempts every token.
Original unknown first errors (including undefined) survive later cleanup faults.
Bank retains only copied jobs/readers with its existing512B/job owner; original
admission input/asset retention is unchanged. Estimates are accounting, not a
particular JavaScript allocator/GC or physical GPU memory guarantee.
