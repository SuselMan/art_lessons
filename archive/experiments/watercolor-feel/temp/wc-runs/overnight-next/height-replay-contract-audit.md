# Ограничение будущего H по существующему контракту

Проверено в текущем worktree cbef03b5: `packages/shared/src/stroke.ts`, `operationBase.ts`, `apps/web/src/engine/src/paper/paperWetness.ts`, `_paintDabs` в index.ts. Это read-only исследование; существующий контракт не изменён.

Dab.t — время относительно первого отпечатка штриха. StrokeOperation.wet — записанная квантованная реакция среды под каждым dab. washId — уже принятое live решение группировки. PaperWetness намеренно локально/эфемерно, не replay state; deposit берёт max состояния, а не сумму объёма; pending вода текущего жеста видна экрану, но не sampler модели до commit. Undo лужи не вычисляет заново реакцию уже зависимого штриха.

Нельзя назвать геометрический CPU H текущим PaperWetness, нельзя считать его P.A, и нельзя автоматически восстанавливать полную исходную2D лужу только по одномерному wet profile. Наличие OperationBase.timestamp не является согласованным разрешением заново симулировать реальные межштриховые часы: timestamp/seq и локальные clocks разных авторов не дают доказанной эквивалентности текущему baked interaction.

В next-h-webgl1-feasibility.md фраза про evaporation по recorded timestamps — гипотеза будущего изменения семантики, а не текущая возможность/решение. До такого решения безопасный CPU/GPU эксперимент H должен явно оставаться stroke/wash-local fixture с заданными H-init и неподвижным recorded wet profile. Для внедрения необходимы отдельные решения о meaning/source/lifecycle и совместимости live/replay/undo/checkpoint, с явным сравнением действующего поведения. Этого в ночных пробах не сделано.

Следствие для листа4: два реальных washId, prior-water footprint и injectedH proxy дают исследовательский контроль, но внедрять постоянную межштриховую H-карту по этому одному результату преждевременно. Для листов6/9 можно сначала исследовать H только в текущем gesture scratch и хронологический перенос при фиксированных записанных мокрых взаимодействиях; это отдельный путь проверки, не утверждение готовности.

Дополнительное численное ограничение WebGL1: RG-пакет16bit не гарантирует16bit арифметику шейдера. Для точного представления целых0..65535 при decode/edge allocation требуется проверенная fragment highp precision; mediump может потерять младшие коды. getShaderPrecisionFormat/реальная компиляция и CPU/GPU byte parity обязательны. Даже при highp операции fraction/floor на границе целого требуют проверки; сам факт roundtrip двух байтов в CPU недостаточен.
